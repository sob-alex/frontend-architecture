# Frontend Architecture Principles

Общие принципы проектирования frontend-приложений.

Документ определяет архитектурные правила, обязательные для новых проектов и применяемые при развитии и рефакторинге существующих.

Правила не зависят от используемого фреймворка, размера приложения и выбранного набора FSD-слоёв.

## 1. Функциональная декомпозиция

**Принцип: код должен группироваться по функциональной ответственности, а не только по техническому назначению.**

Основной единицей организации приложения является функциональный модуль (slice), объединяющий связанный код.

Не рекомендуется использовать глобальную организацию всего приложения исключительно по техническим категориям:

```text
src/
├── components/
├── hooks/
├── stores/
├── services/
└── utils/
```

Такая структура распределяет связанную функциональность по разным частям проекта и затрудняет её сопровождение по мере роста приложения.

Предпочтительна организация по функциональным областям:

```text
features/
├── add-to-cart/
│   ├── ui/
│   ├── model/
│   └── api/
└── submit-order/
    ├── ui/
    ├── model/
    └── api/
```

При этом внутри функциональных модулей допускается разделение по техническому назначению: `ui`, `model`, `api`, `lib` и другие.

### Правила

- Связанный код должен располагаться максимально близко.
- Модуль должен иметь понятную и ограниченную ответственность.
- Внутренняя организация модуля не должна становиться глобальной организацией всего приложения.
- Выделение нового slice должно иметь функциональное обоснование.
- Не следует преждевременно дробить функциональность на множество мелких modules и slices.

Для небольших проектов функциональная декомпозиция может ограничиваться страницами и крупными блоками интерфейса.

## 2. Однонаправленные зависимости

**Принцип: зависимости между архитектурными модулями должны быть направленными, предсказуемыми и не образовывать циклов.**

На уровне проекта используются правила FSD:

```text
app
 ↓
pages
 ↓
widgets
 ↓
features
 ↓
entities
 ↓
shared
```

Модуль может импортировать код из слоёв, расположенных ниже, но не выше.

Допускается пропуск промежуточных слоёв.

Например, `pages` может напрямую использовать `shared/ui`.

### Правила

- Импорты между FSD-слоями направлены только сверху вниз.
- Slices одного слоя не должны напрямую импортировать друг друга.
- Внутренние файлы одного slice могут взаимодействовать между собой с соблюдением его собственных архитектурных границ.
- Циклические зависимости между модулями запрещены.
- `shared` не должен зависеть от вышестоящих FSD-слоёв.
- Исключения из стандартных правил FSD должны быть явно описаны и обоснованы.

Слои `app` и `shared` не содержат обычных FSD-slices и имеют особые правила внутренней организации.

Подробные правила и допустимые исключения описываются в [FSD](FSD.md.md).

## 3. Инкапсуляция и Public API

**Принцип: внешний код должен зависеть от публичного контракта модуля, а не от его внутренней реализации.**

Каждый выделенный slice предоставляет публичный интерфейс для взаимодействия с другими модулями.

Пример:

```text
features/
└── add-to-cart/
    ├── ui/
    │   └── AddToCartButton.tsx
    ├── model/
    │   └── useAddToCart.ts
    └── index.ts
```

Публичный API:

```ts
// features/add-to-cart/index.ts

export { AddToCartButton } from './ui/AddToCartButton';
```

Корректное использование:

```ts
import { AddToCartButton } from '@/features/add-to-cart';
```

Некорректное использование из другого slice:

```ts
import { AddToCartButton } from
  '@/features/add-to-cart/ui/AddToCartButton';
```

### Правила

- Другие slices обращаются к модулю через его Public API.
- Внутренняя структура slice считается деталью реализации.
- Публичный API должен содержать только действительно необходимые экспорты.
- Внутри собственного slice разрешены прямые относительные импорты.
- Изменение внутренней реализации не должно без необходимости затрагивать потребителей модуля.

Для `shared` допускаются публичные API отдельных сегментов, например `shared/ui` и `shared/lib`, вместо единой точки экспорта всего слоя.

## 4. Разделение ответственности

**Принцип: код с разными причинами изменения должен иметь различимые зоны ответственности.**

Для frontend выделяются следующие логические области:

| Область | Ответственность |
|---|---|
| Presentation | Отображение, пользовательский ввод, UI-состояние |
| Application | Сценарии и координация операций |
| Domain | Бизнес-модели, правила и инварианты |
| Infrastructure | HTTP, storage, SDK, внешние сервисы и адаптеры |

Это логические границы, а не обязательные директории.

Один slice может содержать несколько таких областей.

### Правила

- UI не должен становиться основным местом хранения бизнес-правил.
- Domain не должен зависеть от UI, фреймворков и инфраструктуры.
- Application-логика не должна зависеть от конкретных технических реализаций внешних сервисов.
- Инфраструктурный код отвечает за интеграции с внешним миром.
- Простые сценарии не требуют обязательного выделения отдельного Application-слоя.

Разделение должно быть достаточным, чтобы изменения в одной области не приводили к необоснованным изменениям в остальных.

Подробнее: [Clean Architecture](clean-architecture.md.md).

## 5. Независимость бизнес-логики

**Принцип: бизнес-правила должны быть независимы от технологий, используемых для их выполнения и отображения.**

Бизнес-логика не должна напрямую зависеть от:

- React, Vue, Astro и других UI-фреймворков;
- Redux, Zustand, Pinia и других state managers;
- HTTP-клиентов и конкретных API endpoints;
- браузерных API и механизмов хранения данных;
- внешних DTO и форматов интеграции.

Пример чистой бизнес-функции:

```ts
// model.ts

export function calculateDiscount(
  price: number,
  percent: number,
): number {
  if (percent < 0 || percent > 100) {
    throw new Error('Invalid discount');
  }

  return price * (1 - percent / 100);
}
```

Функция не знает, откуда получены значения и где будет отображён результат.

Её можно тестировать независимо от интерфейса и внешнего окружения.

### Правила

- Бизнес-правила размещаются в framework-independent модулях.
- Внешние зависимости не импортируются в чистое доменное ядро.
- Побочные эффекты выносятся за пределы чистых доменных функций.
- Время, случайность и другие изменяемые внешние значения передаются явно, если они влияют на бизнес-правила.
- Доменные функции должны быть доступны для изолированного тестирования.

Важно: FSD-сегмент `model` может содержать не только бизнес-логику, но и stores, hooks и другую логику состояния.

Поэтому независимость требуется именно от **чистого доменного кода**, а не автоматически от всех файлов внутри `model`.

При необходимости доменная логика выделяется в отдельный файл или подкаталог.

## 6. Dependency Inversion

**Принцип: внутренние бизнес-сценарии не должны зависеть от конкретных реализаций внешних систем.**

Если Application-логика взаимодействует с внешним сервисом, её зависимости могут быть выражены через контракты.

Например:

```ts
interface OrderRepository {
  save(order: Order): Promise<void>;
}
```

Use Case работает с контрактом:

```ts
async function createOrder(
  order: Order,
  repository: OrderRepository,
) {
  await repository.save(order);
}
```

Конкретная реализация репозитория находится во внешнем адаптере и передаётся в сценарий через композицию зависимостей.

### Правила

- Сложные бизнес-сценарии не должны импортировать конкретные HTTP/storage-адаптеры.
- Контракты располагаются со стороны кода, которому требуется соответствующая возможность.
- Реализации контрактов могут заменяться без изменения бизнес-правил и сценариев.
- Создание и связывание зависимостей выполняется за пределами чистого ядра.
- Интерфейсы и Dependency Injection вводятся там, где есть реальная потребность в такой границе.

Не требуется создавать Repository Interface для каждого API-запроса.

Простой запрос через TanStack Query или аналогичный инструмент может использоваться без отдельного Use Case и Repository, если самостоятельная Application-логика отсутствует.

## 7. Разделение UI-состояния и бизнес-логики

**Принцип: механизмы управления состоянием не должны становиться единственным местом реализации бизнес-правил.**

Состояние интерфейса и бизнес-логика имеют разные обязанности.

К UI-состоянию относятся, например:

- открытие модальных окон;
- выбранные вкладки;
- раскрытие меню;
- состояние фокуса;
- временные значения форм;
- loading/error состояния.

Такую логику допустимо размещать непосредственно в компонентах, hooks, composables или stores.

Бизнес-правила, например расчёт скидок, разрешённые переходы статусов и ограничения операций, должны быть доступны отдельно от конкретного state manager.

### Правила

- Локальное состояние не нужно выносить в отдельный модуль без необходимости.
- Бизнес-правила не должны быть жёстко связаны со store.
- Store или hook может координировать выполнение сценария и обновлять состояние интерфейса.
- Не следует дублировать одинаковые бизнес-правила в разных компонентах и stores.
- Замена state manager по возможности не должна требовать переписывания доменной логики.

## 8. Изоляция внешних интеграций

**Принцип: детали взаимодействия с внешними системами должны быть локализованы.**

К внешним интеграциям относятся:

- REST и GraphQL;
- WebSocket и SSE;
- localStorage и IndexedDB;
- сторонние SDK;
- внешние сервисы аналитики;
- другие браузерные и платформенные API.

Код, работающий с этими механизмами, должен иметь определённое место и ответственность.

### Правила

- API-вызовы не должны быть произвольно распределены по компонентам.
- Транспортные детали не должны проникать в доменные правила.
- DTO и внутренние бизнес-модели разделяются, когда их структуры или жизненные циклы различаются.
- Преобразования DTO выполняются на границе взаимодействия с внешним сервисом.
- Общая техническая инфраструктура может размещаться в `shared/api`, а специфичная для функциональности — внутри соответствующего slice.

Создавать отдельный mapper для каждого DTO необязательно. Необходимость преобразования определяется особенностями внешнего контракта и внутренней модели.

## 9. Композиция и переиспользование UI

**Принцип: UI-компоненты должны размещаться по уровню ответственности, а не исключительно по факту переиспользования.**

Рекомендуемое разделение:

| Компонент | Предпочтительное размещение |
|---|---|
| Button, Input, Modal | `shared/ui` |
| Header, Footer | `widgets`, если это самостоятельные композиционные блоки |
| Hero, Testimonials | `widgets`, если переиспользуются как крупные композиционные блоки |
| Уникальная секция страницы | Внутри соответствующего page slice |
| ProductCard | `entities/product/ui`, если это представление бизнес-сущности |
| AddToCartButton | `features/add-to-cart/ui`, если это часть самостоятельной функциональности |

### Правила

- `shared/ui` предназначен преимущественно для универсальных UI-примитивов и независимых компонентов.
- `widgets` используется для крупных самостоятельных блоков интерфейса.
- UI, относящийся исключительно к одной странице, может оставаться внутри неё.
- Компоненты не следует переносить в `shared` только потому, что они используются более одного раза.
- Выделение общего компонента должно сохранять понятный контракт и ответственность.

Использование компонентов из `shared/ui` не запрещает размещать композицию в `shared/ui`, если сама композиция остаётся универсальной и не несёт специфичной продуктовой ответственности.

## 10. Минимально достаточная структура

**Принцип: логическое разделение ответственности не требует обязательного физического разделения на множество файлов и каталогов.**

Архитектурные принципы должны соблюдаться на проектах любой сложности.

При этом допустима компактная организация кода.

Простой модуль:

```text
price-calculator/
├── model.ts
└── ui/
    └── PriceCalculator.tsx
```

Более сложный:

```text
price-calculator/
├── model/
│   ├── domain.ts
│   ├── calculatePrice.ts
│   └── ports.ts
├── api/
│   └── pricingAdapter.ts
├── ui/
│   └── PriceCalculator.tsx
└── index.ts
```

Оба варианта могут соответствовать Clean Architecture.

### Правила

- Не создавать пустые каталоги ради шаблона.
- Не выделять отдельный файл для каждой функции без обоснования.
- Не создавать Use Cases и Repository Interfaces автоматически.
- Разделять файлы при появлении самостоятельных обязанностей.
- Усложнять структуру тогда, когда это повышает читаемость, тестируемость или изменяемость.
- Не смешивать несовместимые архитектурные обязанности только ради сокращения количества файлов.

Один файл может содержать несколько логически связанных функций. Но его компактность не должна нарушать направление зависимостей.

## 11. Pages First и постепенная декомпозиция

**Принцип: начинать с локальной реализации функциональности и выделять самостоятельные модули по мере возникновения необходимости.**

Для небольших и новых приложений предпочтительно начинать с реализации страницы.

Код остаётся внутри page slice, пока не возникает оснований для выделения самостоятельных widgets, features или entities.

Основаниями могут быть:

- появление переиспользования;
- выделение самостоятельной функциональной ответственности;
- рост сложности логики;
- необходимость независимого тестирования;
- чрезмерная связанность или большой размер модуля.

При этом предварительно известные устойчивые бизнес-границы допустимо выделять сразу.

**Не требуется ждать фактического дублирования кода, если самостоятельная ответственность модуля уже очевидна.**

Подробнее: [Project Levels](project-levels.md.md).

## 12. Тестируемость

**Принцип: важные бизнес-правила и сценарии должны быть проверяемы независимо от представления.**

Рекомендуется разделять тестирование по ответственности:

- Domain — unit-тесты бизнес-правил.
- Application — тесты сценариев с подставными зависимостями.
- Infrastructure — тесты интеграций, адаптеров и преобразований данных.
- Presentation — компонентные и пользовательские тесты.

### Правила

- Бизнес-правила не должны требовать запуска UI для проверки.
- Внешние зависимости должны быть заменяемы в тестах там, где это необходимо.
- Приоритет тестирования определяется риском и сложностью поведения.
- Не следует создавать дополнительные абстракции исключительно ради возможности написать trivial unit-тест.

Для статических страниц без самостоятельных бизнес-правил основное внимание может уделяться визуальным, доступностным и интеграционным проверкам.

## 13. Контролируемые архитектурные изменения

**Принцип: изменение архитектуры должно иметь понятную причину и ожидаемую пользу.**

Архитектурные решения принимаются на основе реальных требований, а не предполагаемой сложности, которая может никогда не возникнуть.

Перед введением новой абстракции необходимо оценить:

- Какую проблему она решает?
- Какие зависимости или обязанности она разделяет?
- Насколько решение проще существующих альтернатив?
- Можно ли отложить усложнение без существенных потерь?
- Будет ли решение понятно другим разработчикам?

Следует избегать двух крайностей:

**Недостаточная архитектура** — отсутствие границ, сильная связанность и смешение обязанностей.

**Избыточная архитектура** — множество абстракций, интерфейсов и слоёв без реальной пользы.

Цель стандарта — поддерживать баланс между ними.

## 14. Применение при рефакторинге

Архитектурные правила применяются ко всем новым модулям.

Для существующих проектов допускается постепенное устранение нарушений.

### Правила

- Не требуется переписывать весь проект ради перехода на FSD.
- Новая функциональность должна по возможности соответствовать целевой архитектуре.
- При изменении старого модуля рекомендуется улучшать его архитектурные границы в рамках задачи.
- Рефакторинг не должен менять пользовательское поведение без соответствующих требований.
- Масштабные изменения архитектуры должны сопровождаться проверками и оценкой рисков.

Подробности: [Migration](migration.md.md).

## 15. Архитектурный чек-лист

Перед добавлением нового модуля или при code review рекомендуется проверить:

- [ ] Код расположен в модуле с соответствующей функциональной ответственностью.
- [ ] Соблюдаются правила зависимостей между FSD-слоями.
- [ ] Нет запрещённых импортов между slices одного слоя.
- [ ] Нет циклических зависимостей.
- [ ] Внешние потребители используют Public API модуля.
- [ ] Бизнес-правила не зависят от UI-фреймворка и инфраструктуры.
- [ ] UI, Application и Infrastructure не смешивают несвязанные обязанности.
- [ ] Внешние интеграции локализованы.
- [ ] Важная бизнес-логика может тестироваться отдельно от UI.
- [ ] Новые абстракции имеют конкретное назначение.
- [ ] Структура не содержит ненужных каталогов и формальных архитектурных слоёв.

Пункты применяются с учётом функциональности модуля. Например, у статического UI-компонента могут отсутствовать Domain, Application и внешние интеграции.

## Итог

Архитектура определяется не количеством файлов и директорий, а ответственностью модулей и направлением зависимостей.

**Функциональная декомпозиция обеспечивает понятную структуру проекта. Clean Architecture обеспечивает независимость бизнес-логики от внешних деталей. Прогрессивная организация файлов позволяет применять эти принципы без избыточной сложности.**
