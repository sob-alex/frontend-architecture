# Migration & Refactoring Guidelines

## 1. Назначение

Документ описывает подход к постепенному рефакторингу существующих frontend-проектов и приведению их архитектуры к корпоративному стандарту.

Основные цели миграции:

- улучшить структуру и поддерживаемость проекта;
- локализовать связанную функциональность;
- устранить нежелательные зависимости между модулями;
- отделить бизнес-логику от UI и инфраструктуры;
- сократить технический долг;
- упростить развитие проекта и онбординг разработчиков.

Миграция основывается на сочетании Feature-Sliced Design и принципов Clean Architecture.

**Цель миграции — не создать правильную структуру папок, а улучшить архитектурные границы и снизить связанность приложения.**

Рефакторинг должен проводиться постепенно, с контролем рисков и сохранением существующего поведения.

## 2. Основные принципы миграции

### 2.1. Инкрементальный подход

Предпочтительна постепенная миграция отдельных функциональных областей.

Не рекомендуется одновременно реорганизовывать весь проект, если этого не требуют критические архитектурные проблемы.

Преимущества:

- меньший риск регрессий;
- возможность проверять изменения небольшими частями;
- упрощение code review;
- сохранение возможности параллельной продуктовой разработки;
- возможность корректировать подход по результатам первых этапов.

Миграция может выполняться как отдельными задачами, так и в рамках развития существующей функциональности.

### 2.2. Сохранение поведения

Архитектурный рефакторинг по умолчанию не должен изменять пользовательское поведение приложения.

Необходимо сохранять:

- функциональные сценарии;
- публичные маршруты;
- пользовательские интерфейсы;
- контракты внешних интеграций;
- бизнес-правила;
- ожидаемое поведение состояния и кеширования.

Любые намеренные изменения поведения должны быть явно выделены и согласованы.

### 2.3. Минимально достаточные изменения

Не следует расширять область рефакторинга без необходимости.

Например, перенос компонента в новый slice не требует одновременного:

- переписывания компонента;
- замены state manager;
- обновления всех зависимостей;
- изменения API-клиента;
- переименования всех типов;
- переработки дизайн-системы.

Такие изменения желательно выполнять отдельно, если они не являются обязательными для безопасного завершения миграции.

### 2.4. Архитектурные принципы важнее структуры

Переименование каталогов не гарантирует улучшения архитектуры.

Например:

```text
components/
services/
stores/
```

можно формально преобразовать в:

```text
features/
entities/
shared/
```

Но если нежелательные зависимости и смешение обязанностей сохраняются, архитектурная проблема остаётся.

**Результатом миграции должны быть понятные границы модулей, а не только новая файловая структура.**

## 3. Нужно ли вообще проводить миграцию?

Перед началом необходимо оценить пользу архитектурных изменений.

Возможные причины для миграции:

- сложно найти код, относящийся к определённой функциональности;
- изменения одного модуля часто затрагивают несвязанные области;
- присутствуют циклические зависимости;
- компоненты, stores и API содержат смешанную бизнес-логику;
- новые разработчики тратят много времени на изучение структуры;
- повторяющаяся функциональность реализована несколькими несовместимыми способами;
- существующая архитектура затрудняет тестирование;
- добавление новых возможностей становится неоправданно дорогим.

Если текущая структура хорошо справляется со своими задачами и не создаёт заметных проблем, масштабная миграция может быть нецелесообразной.

В таком случае достаточно применять архитектурные принципы при добавлении новой функциональности и локальном рефакторинге.

## 4. Этап 1. Архитектурный аудит

Перед миграцией необходимо изучить текущее состояние проекта.

### 4.1. Анализ структуры

Определить:

- основные точки входа;
- систему маршрутизации;
- основные страницы;
- функциональные области;
- UI-компоненты;
- управление состоянием;
- API-интеграции;
- общие библиотеки и утилиты;
- зависимости между модулями.

Пример существующей структуры:

```text
src/
├── components/
│   ├── ProductCard.tsx
│   ├── Header.tsx
│   └── CartButton.tsx
├── hooks/
│   └── useCart.ts
├── services/
│   ├── productApi.ts
│   └── cartApi.ts
├── stores/
│   └── cartStore.ts
├── utils/
│   └── calculateDiscount.ts
└── pages/
    ├── Catalog.tsx
    └── Cart.tsx
```

Необходимо определить, какие файлы относятся к одной функциональности и какие зависимости существуют между ними.

### 4.2. Анализ зависимостей

Найти:

- циклические зависимости;
- зависимости между несвязанными функциональными областями;
- импорты из внутренних файлов чужих модулей;
- глобальные модули со слишком большим количеством потребителей;
- обратные зависимости;
- неявные зависимости через глобальное состояние;
- дублирование бизнес-правил.

Отдельно рекомендуется выявить модули с высокой связанностью и большим количеством зависимых потребителей.

Для анализа могут использоваться инструменты построения dependency graph, ESLint и специализированные архитектурные линтеры.

### 4.3. Анализ бизнес-логики

Найти места, где бизнес-правила смешаны с технической реализацией.

Типичные проблемы:

```text
React Component
├── HTTP requests
├── DTO mapping
├── Business validation
├── Business calculations
├── State management
└── UI rendering
```

Или:

```text
Redux / Pinia Store
├── API requests
├── Business rules
├── Data transformation
└── Presentation state
```

Такие модули являются кандидатами на разделение ответственности.

При этом не вся логика компонентов должна выноситься отдельно. Локальное UI-поведение может оставаться внутри компонента.

### 4.4. Анализ тестов и проверок

Оценить:

- существующие unit-тесты;
- компонентные тесты;
- интеграционные тесты;
- E2E-проверки;
- тесты API-контрактов;
- визуальное регрессионное тестирование;
- существующие проверки TypeScript, ESLint и сборки.

Если тестов недостаточно, необходимо определить минимальный набор проверок для безопасной миграции.

Результатом аудита должен стать перечень архитектурных проблем и потенциальных областей рефакторинга.

## 5. Этап 2. Определение целевой архитектуры

После аудита необходимо определить целевую организацию проекта.

Не требуется сразу проектировать максимальную структуру FSD.

Начальная основа:

```text
src/
├── app/
├── pages/
└── shared/
```

По необходимости добавляются:

```text
widgets/
features/
entities/
```

Для Astro, Next.js и других фреймворков с файловой маршрутизацией допускается адаптация физической структуры при сохранении логических границ FSD.

Подробнее: [Project Levels](project-levels.md.md).

### 5.1. Определение функциональных областей

Необходимо составить список основных функциональных областей.

Например:

```text
Catalog
Product
Cart
Checkout
Account
```

Затем определить возможных владельцев кода:

```text
pages/catalog/
widgets/product-catalog/
features/add-to-cart/
entities/product/
entities/cart/
```

Это предварительная схема, которая уточняется в процессе миграции.

Не следует создавать все перечисленные slices до появления фактической необходимости.

### 5.2. Определение архитектурных границ

Для сложных функциональных областей определить:

- Presentation;
- Domain;
- Application;
- Infrastructure.

При этом логические области необязательно должны соответствовать отдельным директориям.

Например:

```text
features/checkout/
├── ui/
├── model/
└── api/
```

может быть достаточно для соблюдения Clean Architecture.

### 5.3. Критерии завершения

До начала миграции рекомендуется определить, по каким признакам работа будет считаться завершённой.

Например:

- выбранная функциональность локализована;
- запрещённые зависимости устранены;
- Public API определён;
- доменные правила отделены от UI;
- тесты проходят;
- пользовательское поведение сохранено;
- новые архитектурные нарушения не появились.

Это позволяет избежать бесконечного рефакторинга без понятного результата.

## 6. Этап 3. Приоритизация задач

Не следует рефакторить модули исключительно в порядке их расположения в проекте.

Рекомендуется учитывать:

| Критерий | Приоритет повышается, если |
|---|---|
| Частота изменений | Модуль регулярно дорабатывается |
| Архитектурные нарушения | Есть циклы и нежелательные зависимости |
| Влияние на проект | Модуль используется многими частями приложения |
| Бизнес-критичность | Ошибка может нарушить важный пользовательский сценарий |
| Тестируемость | Существующая структура затрудняет проверки |
| Стоимость изменений | Простые изменения требуют большого количества правок |
| Риск миграции | Изменение можно безопасно выделить и проверить |

Для первой миграции рекомендуется выбирать **небольшую, но достаточно показательную функциональную область**.

Она должна позволять проверить целевую архитектуру без чрезмерного риска.

Крупные и критичные модули лучше мигрировать после того, как команда подтвердит работоспособность выбранного подхода.

## 7. Этап 4. Подготовка безопасной миграции

Перед структурными изменениями необходимо зафиксировать текущее поведение функциональности.

### 7.1. Baseline

Baseline — исходное состояние, с которым будет сравниваться результат миграции.

В зависимости от проекта baseline может включать:

- результаты существующих тестов;
- публичные маршруты;
- API-контракты;
- контрольные пользовательские сценарии;
- скриншоты интерфейса;
- показатели производительности;
- особенности SSR и hydration;
- текущее поведение кеширования.

Если какая-то проверка изначально не проходит, это необходимо зафиксировать отдельно.

**Результат миграции не должен считаться корректным только на основании того, что проект собирается без ошибок.**

### 7.2. Разделение изменений

По возможности следует разделять:

1. Перемещение файлов и исправление импортов.
2. Изменение внутренних зависимостей.
3. Выделение бизнес-логики.
4. Изменение технических реализаций.

Необязательно создавать отдельный Pull Request для каждого шага, но изменения должны оставаться понятными и проверяемыми.

### 7.3. Обратимость

Миграция должна выполняться небольшими этапами, которые можно независимо проверить и при необходимости откатить.

Не рекомендуется накапливать большой объём непроверенных изменений до завершения всей работы.

## 8. Этап 5. Постепенный переход к FSD

Предпочтительный подход — Pages First с постепенным выделением самостоятельных функциональных модулей.

### 8.1. Выделение страниц

Сначала определить границы страниц.

Например:

```text
src/
├── pages/
│   ├── catalog/
│   └── cart/
```

Если используется файловая маршрутизация, route-файлы могут оставаться в предусмотренной фреймворком директории, а логические страницы — в отдельных page slices.

На начальном этапе допускается сохранение временных зависимостей между старым кодом и новыми страницами.

Они должны быть видимы и постепенно устраняться.

### 8.2. Формирование App и Shared

Выделить глобальную конфигурацию и универсальную инфраструктуру.

Например:

```text
app/
├── providers/
├── router/
└── styles/

shared/
├── ui/
├── api/
└── lib/
```

В `app` переносится инициализация приложения.

В `shared` — действительно универсальная техническая функциональность.

Не следует автоматически переносить весь старый `components`, `services` и `utils` в `shared`.

Это может превратить Shared в новое глобальное хранилище несвязанного кода.

При необходимости допускается временный перенос с последующим распределением по владельцам.

### 8.3. Локализация функциональности

Перенести код, относящийся только к одной странице, внутрь соответствующего page slice.

Например, до миграции:

```text
components/CatalogFilters.tsx
hooks/useCatalogFilters.ts
pages/Catalog.tsx
```

После:

```text
pages/catalog/
├── ui/
│   ├── CatalogPage.tsx
│   └── CatalogFilters.tsx
├── model/
│   └── useCatalogFilters.ts
└── index.ts
```

На этом этапе не требуется создавать самостоятельную feature `filter-products`, если функциональность пока принадлежит только странице и не нуждается в независимом выделении.

### 8.4. Устранение cross-imports

После локализации страниц необходимо устранить прямые зависимости между slices одного слоя.

Например:

```text
pages/catalog → pages/cart
```

Возможные решения:

- перенести общий код в подходящий нижестоящий слой;
- объединить функциональность, если границы были определены неправильно;
- выполнить композицию в вышестоящем слое;
- использовать передачу зависимостей через интерфейсы или callbacks;
- сохранить независимые реализации, если преждевременное обобщение принесёт больше проблем.

Не следует переносить специфичную бизнес-логику в `shared` исключительно для обхода запрета cross-imports.

### 8.5. Выделение widgets

Крупные самостоятельные UI-блоки можно выделять в widgets.

Например:

```text
widgets/
├── site-header/
├── product-catalog/
└── site-footer/
```

Основания:

- самостоятельная композиционная ответственность;
- повторное использование;
- сложность блока;
- необходимость независимого сопровождения.

Не требуется превращать каждую секцию страницы в widget.

### 8.6. Выделение features и entities

После формирования понятных границ страниц можно выделять устойчивые функциональные модули.

Например:

```text
features/
└── add-to-cart/

entities/
├── product/
└── cart/
```

Это имеет смысл, если соответствующая логика действительно используется в нескольких сценариях или имеет самостоятельную ответственность.

Не следует заранее дробить весь проект на features и entities без понимания их границ.

### 8.7. Формирование Public API

Для выделенных slices необходимо определить публичные контракты.

Пример:

```ts
// entities/product/index.ts

export { ProductCard } from './ui/ProductCard';
export type { Product } from './model/types';
```

После этого внешние потребители должны импортировать модуль через Public API:

```ts
import { ProductCard } from '@/entities/product';
```

Прямые импорты внутренних файлов другого slice должны быть устранены.

При этом нельзя автоматически экспортировать все внутренние функции и типы. Public API должен оставаться минимальным.

## 9. Этап 6. Внедрение принципов Clean Architecture

Реорганизация по FSD сама по себе не гарантирует отделения бизнес-логики от технических деталей.

Поэтому в процессе миграции необходимо анализировать внутреннюю структуру каждого изменяемого модуля.

### 9.1. Выделение доменных правил

Если бизнес-логика находится внутри компонента:

```tsx
function OrderSummary({ order }) {
  const canPay =
    order.status === 'draft' &&
    order.total > 0;

  // UI
}
```

Её можно выделить в независимую функцию:

```ts
// entities/order/model/rules.ts

export function canPayOrder(order: Order): boolean {
  return order.status === 'draft' && order.total > 0;
}
```

Компонент использует доменную функцию, но правило больше не зависит от React.

Это позволяет тестировать его отдельно.

### 9.2. Разделение UI и Infrastructure

Если компонент напрямую выполняет API-запросы и обрабатывает внешний DTO, рекомендуется выделить инфраструктурную часть.

Например:

```text
features/submit-order/
├── ui/
│   └── SubmitOrderButton.tsx
├── api/
│   └── submitOrder.ts
└── index.ts
```

Для простого сценария этого может быть достаточно.

Не требуется автоматически создавать Use Case и Repository.

### 9.3. Выделение Application Use Cases

Если сценарий содержит:

- несколько последовательных операций;
- сложную координацию;
- бизнес-правила;
- зависимости от нескольких внешних систем;
- необходимость независимого тестирования;

его рекомендуется выделить в Application.

Например:

```text
features/submit-order/
├── ui/
├── model/
│   ├── submitOrder.ts
│   └── ports.ts
├── api/
│   └── httpOrderGateway.ts
└── index.ts
```

Use Case зависит от контрактов, а не от конкретных HTTP-адаптеров.

### 9.4. Разделение состояния

При миграции stores необходимо различать:

- UI-state;
- application orchestration;
- доменные правила;
- технические интеграции.

Не следует автоматически переписывать всё управление состоянием.

Например, существующий Pinia или Redux store может оставаться на месте, пока из него постепенно выделяются независимые бизнес-правила.

Задача — снизить связанность, а не обязательно заменить библиотеку управления состоянием.

## 10. Переходный период

Во время миграции допустимо временное сосуществование старой и новой структуры.

Например:

```text
src/
├── app/
├── pages/
├── features/
├── entities/
├── shared/
│
├── components/     # Legacy
├── services/       # Legacy
└── stores/         # Legacy
```

Это допустимое переходное состояние.

Однако необходимо соблюдать правила:

- новые модули создаются в целевой архитектуре;
- временные зависимости явно учитываются;
- не допускается бесконтрольное расширение старой структуры;
- связанные части переносятся постепенно;
- временные адаптеры не должны превращаться в постоянный обход архитектурных правил.

### Временные адаптеры

Если полное удаление старых зависимостей невозможно сразу, допускается использовать адаптеры и совместимые публичные интерфейсы.

Например, старый модуль может временно делегировать выполнение новой реализации.

При этом рекомендуется избегать двух независимых источников состояния или дублирования бизнес-правил.

Для временных решений желательно фиксировать:

- причину;
- владельца;
- условия удаления;
- связанную задачу или этап миграции.

## 11. Автоматизация архитектурных проверок

Архитектурные правила желательно постепенно переводить в автоматические проверки.

Возможные инструменты:

- ESLint — локальные правила кода и импортов;
- Steiger — проверки архитектуры FSD;
- dependency graph tools — анализ зависимостей и циклов;
- TypeScript — проверка типов;
- unit, integration и E2E tests — проверка поведения.

### 11.1. Начальное внедрение

Если проект уже содержит значительное количество нарушений, необязательно требовать их устранения одним Pull Request.

Сначала можно:

1. Получить исходный отчёт о нарушениях.
2. Зафиксировать существующие проблемы.
3. Включить обязательные проверки для новых или изменяемых областей, если инструменты позволяют ограничить область анализа.
4. Постепенно сокращать количество нарушений.
5. После устранения проблем расширять строгие проверки.

### 11.2. Baseline нарушений

Для существующего проекта допускается вести отдельный список временно разрешённых нарушений.

Важно:

- новые нарушения не должны незаметно добавляться в baseline;
- исправленные нарушения должны удаляться из него;
- исключения должны иметь владельца и объяснение;
- необходимо отслеживать прогресс устранения.

В целевом состоянии архитектурные нарушения должны блокировать CI там, где соответствующее правило является обязательным.

## 12. Проверка результатов миграции

После изменения функционального модуля необходимо подтвердить, что архитектура улучшена, а поведение приложения сохранено.

### 12.1. Статические проверки

- TypeScript;
- ESLint;
- архитектурный линтер;
- анализ циклических зависимостей;
- проверка сборки.

### 12.2. Поведенческие проверки

- unit-тесты бизнес-правил;
- компонентные тесты;
- интеграционные тесты;
- критические E2E-сценарии;
- API-контракты.

### 12.3. Визуальные проверки

Для UI-рефакторинга рекомендуется использовать визуальное регрессионное тестирование.

Например:

```text
Baseline screenshot
        ↓
Refactored screenshot
        ↓
Pixel comparison
        ↓
Diff report
```

В качестве эталона при чисто архитектурном рефакторинге предпочтительно использовать проверенную текущую реализацию интерфейса.

Figma-макеты можно использовать для дополнительной проверки соответствия дизайну, но их различия с текущим продуктом не должны автоматически считаться регрессиями миграции.

### 12.4. Проверки производительности

Если рефакторинг может повлиять на производительность, рекомендуется сравнивать до и после:

- размер JS/CSS bundles;
- количество и состав chunks;
- Core Web Vitals;
- Lighthouse / PageSpeed результаты;
- время загрузки;
- количество сетевых запросов;
- корректность code splitting.

Для SSR/SSG-проектов дополнительно проверить:

- серверный рендеринг;
- hydration;
- генерацию статических маршрутов;
- корректность серверных и клиентских зависимостей.

Для публичных сайтов также важно проверить SEO-значимые элементы: метаданные, canonical URLs, redirects и structured data, если они могли быть затронуты.

## 13. Организация Pull Requests

Архитектурный рефакторинг должен быть удобен для code review.

### Предпочтительный подход

Один Pull Request должен иметь понятную ограниченную цель.

Например:

```text
refactor: isolate product domain rules
refactor: migrate catalog page to FSD
refactor: extract shared site header
refactor: remove cross-imports between pages
```

Не рекомендуется смешивать в одном PR:

- массовые переименования;
- изменение бизнес-правил;
- замену библиотек;
- рефакторинг состояния;
- переработку UI;

если они не являются неразделимыми частями одной задачи.

### Шаблон описания PR

```md
## Цель

Какую архитектурную проблему решает изменение?

## Что изменено

Какие модули и зависимости были изменены?

## Изменения поведения

Отсутствуют / описать намеренные изменения.

## Проверки

- [ ] TypeScript
- [ ] ESLint
- [ ] Архитектурные проверки
- [ ] Unit / Integration tests
- [ ] E2E / Visual regression при необходимости
- [ ] Build

## Риски

Какие области приложения могут быть затронуты?

## Остаточный технический долг

Какие проблемы остаются и почему?
```

Набор проверок выбирается с учётом характера изменений.

## 14. Критерии завершения миграции модуля

Миграцию конкретной функциональности можно считать завершённой, когда:

- код расположен в соответствующем функциональном модуле;
- границы ответственности понятны;
- соблюдается направление зависимостей;
- отсутствуют новые циклические зависимости;
- Public API определён и используется;
- бизнес-правила не зависят от UI и инфраструктуры;
- внешние интеграции локализованы;
- пользовательское поведение сохранено;
- предусмотренные проверки проходят;
- не остаётся незадокументированных временных зависимостей.

Не требуется приводить каждый модуль к максимально подробной файловой структуре.

**Миграция завершена тогда, когда достигнуты архитектурные цели, а не когда созданы все возможные FSD-слои.**

## 15. Отслеживание прогресса

Для крупных миграций рекомендуется вести краткий реестр архитектурных задач.

Пример:

| Область | Проблема | Приоритет | Статус |
|---|---|---|---|
| Catalog | Бизнес-логика внутри UI | Средний | Запланировано |
| Checkout | Смешение API и бизнес-правил | Высокий | В работе |
| Shared UI | Дублирование компонентов | Средний | Не начато |
| Cart | Циклические зависимости | Высокий | Завершено |

Реестр может размещаться в issue tracker проекта.

При оценке прогресса желательно учитывать не только количество перенесённых модулей, но и фактическое устранение проблем:

- уменьшение числа запрещённых зависимостей;
- сокращение циклов;
- уменьшение дублирования бизнес-правил;
- улучшение независимого тестирования;
- локализацию изменений внутри функциональных областей.

Не следует использовать число файлов или slices как самостоятельную метрику качества архитектуры.

## 16. Частые ошибки миграции

### Big Bang Refactoring

Полная реорганизация проекта одним большим изменением.

**Риск:** сложный review, большое число регрессий и длительная интеграция изменений.

Предпочтение: инкрементальная миграция.

### Перемещение файлов без исправления зависимостей

Файлы перенесены в FSD-каталоги, но продолжают напрямую зависеть от несвязанных модулей.

**Риск:** формальная архитектура без фактической изоляции.

Предпочтение: анализировать и корректировать зависимости.

### Shared как временный склад, который стал постоянным

Весь старый код перемещён в `shared`, но не распределён по функциональным владельцам.

**Риск:** сохранение глобальной связанности.

Предпочтение: постепенно переносить специфичную функциональность в соответствующие slices.

### Преждевременное создание Features и Entities

Проект заранее разбивается на большое количество модулей без устойчивых функциональных границ.

**Риск:** увеличение сложности, количества импортов и публичных контрактов.

Предпочтение: Pages First и выделение по реальной ответственности.

### Одновременная замена технологий

Архитектурная миграция сопровождается заменой state manager, HTTP-клиента и UI-библиотеки.

**Риск:** невозможно отделить регрессии рефакторинга от регрессий технологической миграции.

Предпочтение: независимые этапы, если технически возможно.

### Отсутствие проверок

Изменения считаются завершёнными после успешной компиляции.

**Риск:** незамеченные поведенческие, визуальные и интеграционные регрессии.

Предпочтение: использовать проверки, соответствующие изменяемой функциональности.

## 17. Итоговый чек-лист миграции

### До начала

- [ ] Определена конкретная архитектурная проблема.
- [ ] Подтверждена целесообразность рефакторинга.
- [ ] Определена область изменений.
- [ ] Выполнен анализ структуры и зависимостей.
- [ ] Выбрана целевая организация.
- [ ] Зафиксированы необходимые baseline-проверки.
- [ ] Определены критерии завершения.

### Во время миграции

- [ ] Изменения выполняются небольшими этапами.
- [ ] Функциональность локализуется по ответственности.
- [ ] Соблюдаются правила FSD.
- [ ] Чистая бизнес-логика отделяется от UI и инфраструктуры.
- [ ] Public API формируется для новых slices.
- [ ] Не создаются необоснованные абстракции.
- [ ] Временные зависимости контролируются.

### После миграции

- [ ] TypeScript и ESLint проходят.
- [ ] Архитектурные проверки проходят либо известные исключения задокументированы.
- [ ] Пользовательское поведение сохранено.
- [ ] Необходимые тесты пройдены.
- [ ] Визуальные изменения проверены.
- [ ] Производительность и SSR/SSG проверены, если были затронуты.
- [ ] Результаты и остаточный технический долг зафиксированы.
