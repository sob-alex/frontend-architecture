# Feature-Sliced Design

## 1. Назначение

**Feature-Sliced Design (FSD)** — методология организации frontend-приложений, основанная на разделении кода по ответственности, функциональным областям и правилам зависимостей.

В компании FSD используется как основной подход к структурированию frontend-проектов.

Методология определяет:

- архитектурные слои приложения (Layers);
- функциональные модули (Slices);
- внутренние части модулей (Segments);
- правила импортов и взаимодействия модулей;
- публичные интерфейсы модулей (Public API).

FSD применяется совместно с [принципами Clean Architecture](clean-architecture.md.md).

**FSD определяет организацию проекта, Clean Architecture — внутреннюю организацию логики и направление зависимостей.**

## 2. Основные понятия

FSD использует три уровня организации.

```text
Layer
  └── Slice
       └── Segment
```

### Layer

Архитектурный слой, определяющий область ответственности и допустимые зависимости.

Примеры: `pages`, `features`, `entities`.

### Slice

Функциональный модуль внутри слоя.

Slice группирует код, связанный с определённой задачей или понятием предметной области.

Примеры:

```text
features/add-to-cart/
features/submit-order/
entities/product/
entities/user/
pages/catalog/
```

### Segment

Внутренняя часть slice, выделенная по технической ответственности.

Примеры:

```text
ui/
model/
api/
lib/
config/
```

Segments помогают структурировать внутреннюю реализацию, не разделяя связанную функциональность между глобальными директориями.

## 3. Архитектурные слои

FSD определяет шесть основных актуальных слоёв:

```text
app
 ↓
pages
 ↓
widgets
 ↓
features
 ↓
entities
 ↓
shared
```

Стрелки показывают допустимое направление импортов — сверху вниз.

Промежуточные слои можно пропускать.

Например, `pages` вправе напрямую импортировать `entities` или `shared`.

Исторический слой `processes` считается устаревшим и в новых проектах не используется.

### 3.1. App

Слой инициализации и конфигурации приложения.

Типичное содержимое:

```text
app/
├── providers/
├── router/
├── styles/
├── config/
└── main.tsx
```

Здесь размещаются:

- точка входа приложения;
- маршрутизация;
- глобальные providers;
- инициализация состояния;
- глобальные стили;
- интеграции уровня приложения;
- композиция глобальных зависимостей.

`app` может импортировать любой нижестоящий слой.

Слой не разделяется на обычные бизнес-slices.

### 3.2. Pages

Слой отдельных страниц или экранов приложения.

Пример:

```text
pages/
├── home/
├── catalog/
├── product-details/
└── checkout/
```

Каждая страница организуется как самостоятельный slice.

Внутри неё может находиться:

- разметка страницы;
- композиция widgets и features;
- уникальные компоненты страницы;
- локальное состояние;
- специфичные для страницы запросы;
- обработка loading/error состояний.

**Страница не обязана быть тонким композиционным компонентом.**

Если функциональность используется только на одной странице и не имеет причин для отдельного выделения, она может оставаться внутри page slice.

Это соответствует подходу Pages First.

### 3.3. Widgets

Слой крупных самостоятельных блоков интерфейса.

Примеры:

```text
widgets/
├── site-header/
├── site-footer/
├── hero/
├── testimonials/
├── product-catalog/
└── dashboard-sidebar/
```

Widget может:

- объединять несколько UI-компонентов;
- использовать components из `shared/ui`;
- использовать entities и features;
- иметь собственное UI-состояние;
- содержать локальную логику.

**Widget не обязан содержать бизнес-логику.**

Он может быть исключительно композиционным UI-блоком.

#### Когда выделять widget

Рекомендуется выделять widget, если:

1. Блок имеет самостоятельную визуальную или функциональную ответственность.
2. Используется на нескольких страницах.
3. Содержит достаточно сложную композицию интерфейса, которую полезно изолировать от страницы.

Например:

```text
widgets/hero/
├── ui/
│   ├── Hero.astro
│   └── HeroActions.astro
└── index.ts
```

`Hero` может использовать `Button`, `Container` и `Typography` из `shared/ui`.

Это нормальная зависимость:

```text
widgets/hero → shared/ui
```

Если Hero уникален для одной страницы, его допустимо оставить внутри неё:

```text
pages/home/ui/HeroSection.astro
```

**Не нужно автоматически переносить каждую секцию страницы в `widgets`.**

#### Widgets и Shared UI

`shared/ui` содержит универсальные UI-компоненты, которые не реализуют специфическую продуктовую функциональность.

`widgets` содержит законченные композиционные блоки приложения.

Например:

```text
shared/ui/button/
shared/ui/container/
shared/ui/dialog/

widgets/site-header/
widgets/hero/
widgets/contact-section/
```

Использование нескольких компонентов из `shared/ui` само по себе не делает композицию widget.

Главный критерий — ответственность блока и его место в структуре приложения.

### 3.4. Features

Слой пользовательских действий и самостоятельных функциональных возможностей.

Примеры:

```text
features/
├── sign-in/
├── add-to-cart/
├── submit-contact-form/
├── filter-products/
└── change-password/
```

Feature может содержать:

- компоненты взаимодействия;
- состояние функциональности;
- валидацию;
- application-сценарии;
- обращения к API;
- специфичную конфигурацию.

Пример:

```text
features/add-to-cart/
├── ui/
│   └── AddToCartButton.tsx
├── model/
│   └── useAddToCart.ts
├── api/
│   └── addToCart.ts
└── index.ts
```

#### Когда выделять feature

Выделение оправдано, если функциональность:

- имеет самостоятельное назначение;
- используется в нескольких частях приложения;
- содержит сложное взаимодействие или состояние;
- требует независимого сопровождения или тестирования;
- представляет значимую возможность продукта.

Не каждое действие пользователя должно становиться отдельной feature.

Например, простой переключатель вкладок обычно остаётся частью соответствующего UI-компонента.

Если форма обратной связи существует только на одной небольшой странице, её можно оставить внутри page slice.

При усложнении или повторном использовании она может быть выделена в `features/submit-contact-form`.

### 3.5. Entities

Слой основных понятий предметной области приложения.

Примеры:

```text
entities/
├── user/
├── product/
├── order/
└── article/
```

Entity в FSD — не обязательно класс, объект ORM или таблица базы данных.

Это самостоятельное бизнес-понятие, с которым работает приложение.

Пример:

```text
entities/product/
├── model/
│   ├── types.ts
│   └── rules.ts
├── api/
│   └── productApi.ts
├── ui/
│   └── ProductCard.tsx
└── index.ts
```

В `entities` могут находиться:

- доменные типы и модели;
- бизнес-правила;
- работа с данными сущности;
- преобразование внешних данных;
- UI-представление сущности.

При этом необходимо соблюдать разделение ответственности внутри slice.

Например, чистые бизнес-правила из `model/rules.ts` не должны зависеть от `api/productApi.ts`.

#### Когда выделять entity

Entity рекомендуется выделять, если бизнес-понятие:

- используется в нескольких функциональных сценариях;
- содержит собственные правила или состояние;
- требует согласованной модели данных;
- имеет самостоятельную значимость для предметной области.

Не нужно превращать каждый тип TypeScript или каждое поле API в отдельную entity.

### 3.6. Shared

Слой универсальной инфраструктуры и переиспользуемых компонентов без привязки к конкретному бизнес-домену.

Пример:

```text
shared/
├── ui/
│   ├── button/
│   ├── modal/
│   └── container/
├── api/
│   └── httpClient.ts
├── lib/
│   ├── date/
│   └── formatting/
├── config/
└── assets/
```

Слой может содержать:

- UI-kit;
- HTTP-клиенты;
- универсальные утилиты;
- общую конфигурацию;
- работу с окружением;
- базовые технические адаптеры.

`shared` не должен содержать бизнес-логику конкретной функциональности.

Например:

```text
shared/lib/formatDate.ts       ✅
shared/lib/calculateCart.ts    ❌
```

Расчёт корзины должен принадлежать функциональному или доменному модулю.

В отличие от большинства FSD-слоёв, `shared` не разделяется на бизнес-slices.

Внутренние segments `shared` могут взаимодействовать друг с другом, но не должны зависеть от вышестоящих слоёв.

## 4. Правила зависимостей

Основное правило FSD:

**Slice может импортировать другие slices только из нижестоящих слоёв.**

Пример допустимых импортов:

```ts
// pages/catalog/ui/CatalogPage.tsx

import { ProductCatalog } from '@/widgets/product-catalog';
import { ProductCard } from '@/entities/product';
import { Button } from '@/shared/ui/button';
```

Пример запрещённого импорта:

```ts
// entities/product/model/product.ts

import { AddToCartButton } from '@/features/add-to-cart';
```

Нижестоящая сущность не должна зависеть от функциональности, которая её использует.

### 4.1. Зависимости между slices одного слоя

По умолчанию прямые импорты между разными slices одного слоя запрещены.

Например:

```text
features/add-to-cart → features/checkout   ❌
widgets/header → widgets/sidebar          ❌
pages/catalog → pages/home                ❌
```

Если двум slices нужна общая функциональность, предпочтительны следующие решения:

1. Перенести общую логику в подходящий нижестоящий слой.
2. Объединить slices, если они фактически представляют одну функциональность.
3. Организовать композицию через вышестоящий слой.
4. Передать зависимость через props, slots или Dependency Injection.

Осознанные исключения допускаются только при наличии архитектурного обоснования.

### 4.2. Cross-imports между entities

Бизнес-сущности иногда имеют тесные связи.

Например, `Order` может содержать данные `Product`.

В таких случаях рекомендуется сначала рассмотреть возможность:

- объединения связанных моделей;
- использования идентификаторов вместо вложенных сущностей;
- переноса логики взаимодействия на вышестоящий слой.

Если прямую типовую зависимость устранить нецелесообразно, допускается механизм `@x`.

Пример:

```text
entities/
├── product/
│   ├── model/
│   │   └── types.ts
│   └── @x/
│       └── order.ts
│
└── order/
    └── model/
        └── types.ts
```

```ts
// entities/product/@x/order.ts

export type { Product } from '../model/types';
```

```ts
// entities/order/model/types.ts

import type { Product } from '@/entities/product/@x/order';
```

Это специальный Public API, предназначенный для конкретного потребителя.

Использование `@x` должно быть исключением, а не стандартным способом связывания entities.

## 5. Public API

Каждый выделенный slice должен предоставлять контролируемый публичный интерфейс.

Обычно он реализуется через `index.ts`.

```text
features/add-to-cart/
├── ui/
│   └── AddToCartButton.tsx
├── model/
│   └── useAddToCart.ts
└── index.ts
```

```ts
// features/add-to-cart/index.ts

export { AddToCartButton } from './ui/AddToCartButton';
```

Другие slices импортируют модуль через его Public API:

```ts
import { AddToCartButton } from '@/features/add-to-cart';
```

Не допускается обход Public API:

```ts
import { AddToCartButton } from
  '@/features/add-to-cart/ui/AddToCartButton';
```

### Правила

- Экспортировать только необходимый внешний контракт.
- Не использовать массовый `export *` без обоснования.
- Не раскрывать внутренние структуры данных и реализации без необходимости.
- Внутри самого slice использовать прямые относительные импорты.
- Избегать импорта собственного `index.ts` из внутренних файлов slice, чтобы не создавать циклы.

Для `shared` рекомендуется Public API на уровне конкретных компонентов или библиотек:

```ts
import { Button } from '@/shared/ui/button';
import { formatDate } from '@/shared/lib/date';
```

Это позволяет избежать больших barrel-файлов и нежелательных зависимостей между универсальными модулями.

При разделении клиентского и серверного кода допускаются отдельные environment-specific точки экспорта.

## 6. Правила организации segments

Segments создаются по мере необходимости.

Основные соглашения:

| Segment | Назначение |
|---|---|
| `ui` | Компоненты, стили, presentation logic |
| `model` | Модели данных, бизнес-правила, состояние, сценарии |
| `api` | Внешние запросы, DTO, мапперы, адаптеры |
| `lib` | Вспомогательные модули, специфичные для slice |
| `config` | Конфигурация функциональности |

Допускается добавление дополнительных segments, когда это улучшает организацию.

Не нужно создавать пустые директории:

```text
features/contact-form/
├── ui/
├── model/
├── api/
├── lib/
└── config/
```

Если функциональности требуется только UI, достаточно:

```text
features/contact-form/
├── ui/
│   └── ContactForm.tsx
└── index.ts
```

Segments определяют организацию файлов по назначению, но не заменяют внутренние правила Clean Architecture.

Например, наличие `model` не означает, что весь код внутри него автоматически является чистой доменной логикой.

## 7. Pages First

В качестве основного подхода к декомпозиции используется **Pages First**, соответствующий FSD v2.1.

Разработка начинается с отдельных страниц и их функциональности.

Пример начальной структуры:

```text
src/
├── app/
├── pages/
│   ├── home/
│   ├── catalog/
│   └── about/
└── shared/
```

На этом этапе не требуется предварительно определять все будущие features и entities.

По мере развития приложения выделяются новые slices.

Например:

```text
pages/catalog/
    ↓
Появляется повторно используемый каталог
    ↓
widgets/product-catalog/
    ↓
Появляются самостоятельные действия
    ↓
features/filter-products/
    ↓
Появляется общая доменная модель
    ↓
entities/product/
```

Это возможная эволюция, а не обязательная последовательность.

### Принцип выделения

**Код перемещается в самостоятельный slice при появлении устойчивой ответственности, повторного использования или необходимости независимого сопровождения.**

Не следует создавать архитектурные модули исключительно на основании предполагаемого будущего роста.

## 8. Адаптация FSD для Astro

Astro использует файловую маршрутизацию через специальную директорию `src/pages`.

Поэтому для проектов с большим количеством страниц допускается разделение:

- `src/pages` — файлы маршрутов Astro;
- `src/views` — логические page slices, соответствующие слою `pages` методологии FSD.

Пример:

```text
src/
├── pages/
│   ├── index.astro
│   └── about.astro
│
├── views/
│   ├── home/
│   │   ├── ui/
│   │   │   ├── HomePage.astro
│   │   │   └── HeroSection.astro
│   │   └── index.ts
│   └── about/
│       ├── ui/
│       │   └── AboutPage.astro
│       └── index.ts
│
├── app/
│   ├── layouts/
│   └── styles/
│
├── widgets/
│   ├── site-header/
│   └── site-footer/
│
└── shared/
    ├── ui/
    └── assets/
```

`views` — корпоративная адаптация названия FSD-слоя `pages`, а не дополнительный архитектурный слой.

Файлы Astro внутри `src/pages` остаются маршрутными точками входа и подключают логические страницы.

Например:

```astro
---
// src/pages/index.astro

import { HomePage } from '@/views/home';
---

<HomePage />
```

Для совсем небольших сайтов допускается размещение композиции непосредственно в Astro route-файле без отдельного `views`.

Выбранное соглашение должно быть единым внутри конкретного проекта.

При использовании `views` правила межслойных импортов должны учитывать его эквивалентность логическому слою `pages`.

Подробнее: [Astro Landing](./examples/astro-landing.md).

## 9. Масштабирование структуры

Необязательно использовать все слои FSD.

Простой проект:

```text
src/
├── app/
├── pages/
└── shared/
```

Проект с крупными композиционными блоками:

```text
src/
├── app/
├── pages/
├── widgets/
└── shared/
```

Приложение с самостоятельными функциональными областями:

```text
src/
├── app/
├── pages/
├── widgets/
├── features/
├── entities/
└── shared/
```

Выбор структуры определяется реальными обязанностями модулей, а не формальной классификацией проекта.

Один сложный экран может требовать большего архитектурного разделения, чем многостраничный статический сайт.

Подробнее: [Project Levels](project-levels.md.md).

## 10. Рекомендации по именованию

- Layers — стандартные имена FSD в нижнем регистре.
- Slices — kebab-case, отражающий функциональность или бизнес-понятие.
- Segments — имена по ответственности: `ui`, `model`, `api`, `lib`, `config`.
- React/Vue/Astro components — PascalCase.
- Функции и hooks — согласно соглашениям языка и фреймворка.

Примеры:

```text
features/add-to-cart/
features/submit-contact-form/
entities/product/
widgets/site-header/
pages/product-details/
```

Следует избегать слишком абстрактных имён:

```text
features/common/
features/misc/
widgets/other/
```

Имя slice должно помогать разработчику понимать его назначение без чтения внутренней реализации.

## 11. Архитектурные проверки

Соблюдение правил FSD рекомендуется проверять автоматически.

Базовые проверки:

- направление импортов между layers;
- запрещённые cross-imports между slices;
- обход Public API;
- циклические зависимости;
- соответствие структуры согласованным соглашениям.

Для проверки может использоваться [Steiger](https://github.com/feature-sliced/steiger) совместно с ESLint и другими инструментами анализа зависимостей.

Для проектов с адаптированной структурой, например Astro с `views`, необходимо отдельно настроить правила распознавания архитектурных слоёв.

Архитектурные нарушения должны выявляться в CI и code review, а не только при ручном аудите.

## 12. Контрольный список

Перед выделением нового slice рекомендуется проверить:

- [ ] У модуля есть самостоятельная ответственность.
- [ ] Выбран соответствующий FSD-слой.
- [ ] Модуль не дублирует существующую функциональность.
- [ ] Нет запрещённых импортов между slices.
- [ ] Соблюдается направление зависимостей.
- [ ] Публичный API содержит только необходимое.
- [ ] Внутренняя структура не раскрывается потребителям.
- [ ] Не создаются пустые или необоснованные segments.
- [ ] Бизнес-логика отделена согласно Clean Architecture.
- [ ] Новое выделение упрощает сопровождение и навигацию по проекту.
