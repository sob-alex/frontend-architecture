 # Frontend Architecture Guidelines

Единый архитектурный стандарт для разработки и сопровождения frontend-проектов компании.

## 1. Цель

Этот документ описывает общий подход к организации frontend-приложений независимо от их размера, сложности и используемого технологического стека.

Стандарт применяется к новым проектам и используется как ориентир при рефакторинге существующих.

Основные цели:

- **Единообразие** — предсказуемая структура и общие архитектурные правила между проектами.
- **Масштабируемость** — возможность развивать приложение без необходимости полностью пересматривать архитектуру.
- **Поддерживаемость** — локализация изменений и снижение связанности между модулями.
- **Тестируемость** — возможность проверять бизнес-логику независимо от UI и внешних сервисов.
- **Быстрый онбординг** — снижение времени на знакомство разработчиков с новыми проектами.
- **Разумная сложность** — отсутствие лишних абстракций, каталогов и архитектурных слоёв.

Архитектура должна помогать разработке, а не усложнять её.

## 2. Основной подход

В качестве архитектурной основы используется сочетание двух подходов.

### Feature-Sliced Design (FSD)

Определяет организацию проекта:

- группировку кода по функциональности и ответственности;
- архитектурные слои (layers);
- функциональные модули (slices);
- внутреннюю структуру модулей (segments);
- направление зависимостей;
- публичные интерфейсы модулей (Public API).

FSD отвечает на вопрос: **где должен находиться код и как модули взаимодействуют друг с другом?**

### Clean Architecture Principles

Определяют правила организации логики:

- отделение бизнес-правил от представления и инфраструктуры;
- направление зависимостей к бизнес-логике;
- разделение ответственности;
- независимость доменной логики от фреймворков и внешних сервисов;
- использование Dependency Inversion там, где это необходимо.

Clean Architecture отвечает на вопрос: **как организовать код внутри модуля, чтобы его логика не зависела от деталей реализации?**

### Общая концепция

**FSD — для организации проекта и границ модулей. Clean Architecture — для внутренних зависимостей и разделения ответственности.**

Оба подхода применяются совместно и не рассматриваются как альтернативы.

## 3. Прогрессивная архитектура

Во всех проектах используются одни и те же архитектурные принципы, но их физическая реализация зависит от сложности приложения.

Это означает:

- Необязательно использовать все слои FSD.
- Необязательно создавать все возможные segments внутри каждого slice.
- Необязательно выделять Domain, Application и Infrastructure в отдельные директории.
- Не нужно создавать Use Cases, Repository Interfaces и Adapters для каждого действия.
- Связанная функциональность должна оставаться локализованной в рамках своего модуля.
- При увеличении сложности код постепенно разделяется на более специализированные модули.

**Архитектурные правила остаются постоянными; количество файлов, каталогов и абстракций увеличивается только при необходимости.**

Например, для небольшого лендинга могут быть достаточны:

```text
app/
pages/
widgets/
shared/
```

Для сложного приложения могут использоваться все основные слои FSD:

```text
app/
pages/
widgets/
features/
entities/
shared/
```

Набор директорий не является критерием качества архитектуры.

Если в проекте нет бизнес-логики, создавать искусственный Domain-слой не требуется. Однако при появлении бизнес-правил они должны быть отделены от UI и внешних технических деталей.

Подробнее: [Уровни сложности проектов](project-levels.md.md).

## 4. Область применения

Стандарт предназначен для frontend-проектов различных типов:

- статические сайты и лендинги;
- многостраничные корпоративные сайты;
- интерактивные веб-приложения;
- личные кабинеты и административные панели;
- сложные продуктовые интерфейсы.

Подход не привязан к конкретному фреймворку и может адаптироваться для React, Vue, Astro и других технологий.

Особенности файловой маршрутизации, SSR, SSG, состояния и используемых инструментов учитываются в примерах для конкретных стеков.

**Фреймворк может влиять на физическую структуру проекта, но не должен отменять основные архитектурные принципы.**

## 5. Применение стандарта

### Новые проекты

1. Определить основные функциональные области приложения.
2. Выбрать минимально достаточный набор FSD-слоёв.
3. Начать с реализации страниц и необходимой функциональности.
4. Выделять переиспользуемые и самостоятельные модули по мере необходимости.
5. Соблюдать правила зависимостей и разделения ответственности с начала разработки.
6. Добавлять архитектурные абстракции при появлении реальной сложности.

### Существующие проекты

Полный переход на FSD не является обязательным условием дальнейшей разработки.

Рефакторинг проводится постепенно, начиная с наиболее проблемных участков.

Приоритет отдаётся:

- устранению циклических и нежелательных зависимостей;
- локализации связанного кода;
- отделению бизнес-логики от UI и инфраструктуры;
- формированию понятных границ модулей;
- сокращению технического долга.

Масштабная реорганизация каталогов без измеримой пользы не является самостоятельной целью.

Подробнее: [Миграция существующих проектов](migration.md.md).

## 7. Приоритет правил

Архитектурные решения разделяются на две категории.

**Обязательные правила**

Правила, нарушение которых приводит к нежелательным зависимостям, размыванию ответственности или ухудшению поддерживаемости.

Они должны соблюдаться во всех новых модулях и учитываться при изменении существующих.

**Рекомендации**

Предпочтительные способы организации кода, которые могут изменяться в зависимости от конкретной задачи.

Отступления допустимы, если они обоснованы и не нарушают обязательные архитектурные принципы.

Неоднозначные или повторяющиеся решения фиксируются в документации, чтобы сохранять единообразие между проектами.
