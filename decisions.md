# Architecture Decisions & FAQ

## 1. Назначение

Документ содержит практические рекомендации по организации frontend-кода.

Его цель — помочь разработчикам принимать единообразные архитектурные решения при создании новой функциональности, развитии существующих проектов и проведении code review.

Документ дополняет:

- [Principles](principles.md.md) — общие обязательные правила;
- [Feature-Sliced Design](FSD.md.md) — организация проекта и зависимости;
- [Clean Architecture](clean-architecture.md.md) — разделение логики и зависимостей;
- [Project Levels](project-levels.md.md) — масштабирование структуры.

Решения ниже представляют принятые соглашения компании. Там, где возможны альтернативы, указаны условия их применения.

**Основной принцип: код должен находиться рядом со своей ответственностью, а архитектурные абстракции должны решать конкретные проблемы.**

## 2. Быстрый выбор расположения кода

| Что разрабатываем | Где размещать по умолчанию |
|---|---|
| Страницу или экран | `pages/<page>` |
| Уникальную секцию страницы | `<page>/ui` |
| Крупный переиспользуемый UI-блок | `widgets/<widget>` |
| Универсальный UI-примитив | `shared/ui` |
| Самостоятельное пользовательское действие | `features/<feature>`, если оправдано выделение |
| Бизнес-сущность | `entities/<entity>`, если нужна самостоятельная модель |
| Чистые бизнес-правила | `model` соответствующего slice |
| Application Use Case | `model` соответствующей feature или page |
| Специфичный API-запрос | `api` соответствующего slice |
| Общий HTTP-клиент | `shared/api` |
| Локальный React hook / Vue composable | Рядом с использующим модулем |
| Универсальную техническую функцию | Тематическая библиотека в `shared/lib` |
| Доменную вспомогательную функцию | `model` или `lib` соответствующего slice |
| Глобальную конфигурацию | `app` или `shared/config` по ответственности |
| Локальные стили | Рядом с UI-компонентом |

Таблица определяет предпочтительное решение, но не отменяет анализ ответственности и зависимостей.

## 3. Как выбрать FSD-слой

### D-01. Когда оставлять код внутри page?

**Решение:** если функциональность принадлежит одной странице и не требует самостоятельного выделения, она остаётся внутри page slice.

Пример:

```text
pages/
└── home/
    ├── ui/
    │   ├── HomePage.tsx
    │   ├── HeroSection.tsx
    │   └── AdvantagesSection.tsx
    └── index.ts
```

Это нормальная организация.

Не требуется выделять `HeroSection` и `AdvantagesSection` в отдельные widgets только потому, что они представляют крупные визуальные секции.

Основания для выделения появляются при повторном использовании, независимой ответственности или существенном усложнении.

### D-02. Когда создавать widget?

**Решение:** widget создаётся для крупного самостоятельного композиционного блока интерфейса.

Примеры:

```text
widgets/
├── site-header/
├── site-footer/
├── hero/
├── testimonials/
├── product-catalog/
└── dashboard-sidebar/
```

Widget особенно полезен, когда блок:

- используется на нескольких страницах;
- содержит самостоятельную UI-композицию;
- объединяет несколько нижестоящих модулей;
- имеет собственную значимую ответственность.

Widget может состоять только из разметки.

Наличие API, состояния или бизнес-логики необязательно.

### D-03. Hero используется на нескольких страницах. Widgets или Shared?

**Решение по умолчанию: `widgets/hero`.**

Например:

```text
widgets/
└── hero/
    ├── ui/
    │   └── Hero.astro
    └── index.ts
```

Hero может использовать:

```text
shared/ui/button
shared/ui/container
shared/ui/typography
```

При этом он остаётся композиционным блоком.

Если Hero является исключительно универсальным UI-примитивом, не содержит продуктовой композиции и может использоваться в произвольном контексте как базовый компонент, допускается размещение в `shared/ui`.

**Критерий: ответственность компонента, а не только количество его зависимостей.**

### D-04. Testimonials используются только на главной странице. Нужно ли создавать widget?

Необязательно.

Предпочтительно:

```text
pages/home/ui/TestimonialsSection.tsx
```

Если блок используется на нескольких страницах, можно выделить:

```text
widgets/testimonials/
```

Если несколько вариантов Testimonials имеют общий повторяемый UI-примитив, допустимо выделить универсальные компоненты отдельно, оставив композицию в page или widget.

Не следует обобщать компоненты только из-за визуального сходства, если их требования и поведение существенно различаются.

### D-05. Чем widget отличается от feature?

**Widget — композиция интерфейса. Feature — самостоятельная функциональная возможность.**

Например:

```text
widgets/product-catalog/
features/add-to-cart/
features/filter-products/
```

Каталог отображает продукты и объединяет пользовательские действия.

Добавление в корзину и фильтрация являются самостоятельными функциональными сценариями, если их выделение оправдано.

Пример взаимодействия:

```text
pages/catalog
    ↓
widgets/product-catalog
    ├── features/add-to-cart
    ├── features/filter-products
    └── entities/product
```

Не следует создавать feature только потому, что компонент интерактивный.

### D-06. Когда создавать feature?

**Решение:** при наличии самостоятельной пользовательской или продуктовой функциональности, которую полезно выделить из страницы.

Основания:

- повторное использование;
- сложные сценарии;
- независимое состояние;
- необходимость отдельного тестирования;
- самостоятельный жизненный цикл функциональности.

Примеры:

```text
features/sign-in/
features/add-to-cart/
features/submit-order/
features/apply-promocode/
```

Не рекомендуется создавать:

```text
features/open-modal/
features/toggle-dropdown/
features/click-button/
```

если это простая локальная UI-логика.

Для небольшого компонента достаточно `useState`, `ref` или другого локального состояния.

### D-07. Когда создавать entity?

**Решение:** когда в приложении появляется устойчивое бизнес-понятие с собственной ответственностью.

Примеры:

```text
entities/user/
entities/product/
entities/order/
```

Создание entity оправдано, если модель:

- используется несколькими сценариями;
- содержит собственные бизнес-правила;
- требует согласованного представления;
- имеет самостоятельную значимость в предметной области.

Не нужно создавать entity для каждого API DTO или TypeScript interface.

Например, тип:

```ts
type ButtonProps = {
  disabled?: boolean;
};
```

не является бизнес-сущностью и не требует `entities/button`.

## 4. Clean Architecture внутри модулей

### D-08. Нужно ли применять Clean Architecture на простом лендинге?

**Да, принципы применяются ко всем проектам.**

Но это не означает обязательного наличия:

```text
domain/
application/
infrastructure/
presentation/
```

Если функциональность состоит только из статической разметки, доменный слой ей не нужен.

Если появляется бизнес-правило, оно должно быть изолировано от UI и инфраструктуры.

Пример:

```text
price-calculator/
├── model.ts
└── ui/
    └── PriceCalculator.tsx
```

`model.ts` содержит чистый расчёт, а UI отображает результат.

Таким образом, архитектурные правила соблюдаются без дополнительных директорий.

### D-09. Когда создавать отдельные Domain, Application и Infrastructure?

**Решение:** когда появляются соответствующие самостоятельные обязанности.

Не нужно создавать все области заранее.

Например, для простой функции:

```text
model.ts
ui/Calculator.tsx
```

достаточно отделить чистую логику от представления.

Если появляется внешний API:

```text
model.ts
api.ts
ui/Calculator.tsx
```

Если появляется многошаговый сценарий с зависимостями:

```text
model/
├── rules.ts
├── useCase.ts
└── ports.ts

api/
└── adapter.ts

ui/
└── Feature.tsx
```

Логические архитектурные границы обязательны, но физическая структура усложняется постепенно.

### D-10. Можно ли хранить бизнес-правила и Use Case в одном файле?

Да, если они тесно связаны, а файл сохраняет понятную ответственность и не создаёт неправильных зависимостей.

Например, небольшой независимый сценарий может содержать и проверку входных данных, и вычисление результата.

Однако при появлении нескольких сценариев, повторно используемых правил или внешних зависимостей рекомендуется разделить код.

Критерии:

- самостоятельная ответственность;
- независимое тестирование;
- разные причины изменения;
- снижение связанности.

Количество строк само по себе не определяет необходимость разделения.

### D-11. Может ли `model` содержать React hooks или Zustand stores?

**Да, согласно FSD.**

Но необходимо различать логическую ответственность файлов.

Пример:

```text
features/checkout/
└── model/
    ├── rules.ts
    ├── submitOrder.ts
    └── useCheckout.ts
```

Здесь:

- `rules.ts` — Domain;
- `submitOrder.ts` — Application;
- `useCheckout.ts` — Presentation Adapter.

Допустимая зависимость:

```text
useCheckout.ts → submitOrder.ts → rules.ts
```

Недопустимая:

```text
rules.ts → useCheckout.ts
```

Если это улучшает понимание структуры, presentation hook можно разместить рядом с UI.

**Чистота определяется направлением импортов, а не названием директории.**

### D-12. Когда создавать Use Case?

Use Case полезен, когда существует самостоятельный application-сценарий.

Например:

```text
SubmitOrder
ApplyPromocode
CalculateInsuranceQuote
ConfirmPayment
```

Основания для выделения:

- несколько последовательных шагов;
- координация доменных правил;
- работа с несколькими зависимостями;
- сложная обработка сценария;
- необходимость отдельного тестирования.

Не требуется Use Case для каждого HTTP-запроса.

Например:

```text
Component
    ↓
TanStack Query
    ↓
productsApi
```

является допустимой структурой для простой загрузки данных без самостоятельной application-логики.

### D-13. Когда создавать Repository Interface или Port?

**Решение:** когда внутреннему сценарию необходима внешняя возможность, от конкретной реализации которой он должен быть независим.

Например:

```ts
interface OrderGateway {
  submit(order: Order): Promise<OrderReceipt>;
}
```

Use Case получает интерфейс извне, а HTTP-адаптер реализует его.

Это полезно для сложных сценариев, тестирования и замены внешних механизмов.

Но не нужно создавать:

```text
ProductRepository
HttpProductRepository
GetProductsUseCase
ProductRepositoryFactory
```

ради единственного простого `GET /products`.

Dependency Inversion должен изолировать реальные зависимости, а не генерировать дополнительные сущности без необходимости.

## 5. Работа с данными и состоянием

### D-14. Где размещать API-запросы?

**Решение:** рядом с функциональностью, которая владеет соответствующей операцией.

Базовые операции с сущностью могут размещаться в:

```text
entities/product/api/
```

Специфичные действия — в:

```text
features/submit-order/api/
```

Запросы, относящиеся исключительно к странице, могут оставаться в:

```text
pages/report/api/
```

Универсальная HTTP-инфраструктура размещается в:

```text
shared/api/
```

Например:

```text
shared/api/httpClient.ts
entities/product/api/getProducts.ts
features/submit-order/api/submitOrder.ts
```

Выбор определяется владельцем функциональности, а не только URL endpoint.

### D-15. Где хранить TanStack Query hooks?

Рядом с функциональностью, которая использует запрос.

Например:

```text
entities/product/
├── api/
│   ├── getProducts.ts
│   └── productQueries.ts
└── index.ts
```

Или:

```text
features/submit-order/
├── api/
│   └── submitOrder.ts
├── model/
│   └── useSubmitOrder.ts
└── index.ts
```

Первый вариант подходит для переиспользуемых запросов сущности, второй — для конкретного сценария.

Query Client и его provider размещаются на уровне `app`.

Не следует создавать одну глобальную директорию `queries` для всех бизнес-областей, если это приводит к распределению связанного кода.

### D-16. Где хранить Zustand, Redux или Pinia store?

**Решение:** рядом с состоянием, за которое отвечает модуль.

Примеры:

```text
entities/session/model/sessionStore.ts
features/filter-products/model/filterStore.ts
widgets/data-table/model/tableStore.ts
```

Глобальные providers и техническая инициализация могут находиться в `app`.

Сам по себе факт использования state manager не означает, что весь store должен находиться в глобальной директории.

Важно отделять:

- presentation state;
- application orchestration;
- доменные бизнес-правила.

Бизнес-правила должны оставаться доступными независимо от конкретного state manager.

### D-17. Где хранить DTO и mapper?

DTO и mapper относятся к границе взаимодействия с внешней системой.

Пример:

```text
entities/product/
├── model/
│   └── types.ts
└── api/
    ├── dto.ts
    ├── mapper.ts
    └── getProduct.ts
```

`model/types.ts` содержит внутреннюю модель.

`api/dto.ts` описывает внешний контракт.

`api/mapper.ts` преобразует внешний формат во внутренний.

Отдельный mapper требуется не всегда.

Если структура ответа API совпадает с нужной внутренней моделью и отдельная адаптация ничего не даёт, можно использовать простой контракт без дополнительного преобразования.

Однако доменная бизнес-логика не должна напрямую зависеть от специфичных полей и форматов внешнего API.

### D-18. Где хранить типы TypeScript?

Типы размещаются рядом с кодом, которому они принадлежат.

Примеры:

```text
entities/product/model/types.ts
features/submit-order/model/types.ts
features/submit-order/api/dto.ts
shared/lib/date/types.ts
```

Не рекомендуется создавать глобальную директорию:

```text
src/types/
```

для всех типов приложения.

Общие технические типы допускается размещать в `shared`, если они действительно независимы от бизнес-домена.

Пример универсального типа:

```ts
type Nullable<T> = T | null;
```

Типы, связанные с конкретным продуктом, пользователем или заказом, должны оставаться в соответствующем функциональном или доменном модуле.

### D-19. Где хранить валидацию?

Необходимо разделять два вида валидации.

**Presentation validation**

Отвечает за удобство пользовательского ввода:

- обязательное поле;
- формат email;
- сообщение под полем;
- длина значения;
- состояние ошибки формы.

Размещается рядом с формой или её presentation model.

**Domain validation**

Отвечает за бизнес-инварианты:

- недопустимая скидка;
- запрещённый переход статуса;
- пустой заказ;
- ограничение количества товаров.

Размещается в чистой доменной логике.

Валидация интерфейса не должна быть единственным местом проверки важных бизнес-правил.

Кроме того, frontend-валидация не заменяет проверки на backend.

## 6. Переиспользование и зависимости

### D-20. Компонент используется в двух местах. Нужно ли переносить его в Shared?

**Необязательно.**

Факт повторного использования не определяет архитектурный слой.

Необходимо понять:

- какую ответственность выполняет компонент;
- зависит ли он от бизнес-домена;
- является ли универсальным UI-примитивом;
- является ли композиционным блоком;
- требуется ли ему самостоятельное сопровождение.

Примеры:

```text
Button           → shared/ui
ProductCard      → entities/product/ui
SiteHeader       → widgets/site-header
AddToCartButton  → features/add-to-cart/ui
```

Если два компонента похожи визуально, но имеют разную ответственность, их объединение не всегда оправдано.

### D-21. Две features используют одинаковую бизнес-логику. Куда её вынести?

Сначала необходимо определить владельца логики.

Если это доменное правило, относящееся к устойчивой сущности:

```text
entities/order/model/rules.ts
```

Если это универсальный технический механизм без бизнес-смысла:

```text
shared/lib/
```

Если две features фактически представляют одну связанную функциональность, возможно, их следует объединить.

Не следует автоматически помещать любую повторяющуюся функцию в `shared/lib`.

### D-22. Одна feature должна использовать другую feature. Как поступить?

По корпоративному стандарту прямые cross-imports между features одного слоя запрещены по умолчанию.

Например:

```text
features/checkout → features/promocode
```

Вместо прямой зависимости следует рассмотреть:

1. Композицию обеих features на уровне page или widget.
2. Выделение общей доменной логики в нижестоящий слой.
3. Объединение features, если они образуют единую функциональность.
4. Передачу необходимого поведения через props, callbacks или Dependency Injection.

Например:

```text
pages/checkout/
    ├── features/apply-promocode/
    └── features/submit-order/
```

Страница может координировать взаимодействие, не создавая прямую зависимость между features.

Исключения требуют отдельного архитектурного обоснования.

### D-23. Entity зависит от другой Entity. Что делать?

Предпочтительно избегать прямых зависимостей между entities одного слоя.

Сначала следует рассмотреть:

- объединение связанных моделей;
- представление связи через идентификаторы;
- перенос взаимодействия в вышестоящую feature;
- композицию на уровне page или widget.

Если прямая связь действительно необходима, допускается официальный механизм FSD `@x`.

Пример:

```ts
import type { Product } from '@/entities/product/@x/order';
```

`@x` следует использовать как исключение для обоснованных связей между entities, а не как универсальный способ межмодульных импортов.

### D-24. Где хранить вспомогательные функции?

По области ответственности.

| Функция | Размещение |
|---|---|
| Форматирование даты общего назначения | `shared/lib/date` |
| Форматирование цены без специфичных бизнес-правил | `shared/lib/formatting` |
| Расчёт скидки продукта | `entities/product/model` или владеющий feature slice |
| Преобразование DTO заказа | `entities/order/api` или владеющий feature slice |
| Специфичный helper таблицы | `widgets/data-table/lib` |

Не рекомендуется создавать большие глобальные каталоги `utils` или `helpers` без разделения по тематическим областям.

Каждая общая библиотека должна иметь понятную границу ответственности.

## 7. Особенности UI и фреймворков

### D-25. Где хранить CSS и SCSS?

Локальные стили должны располагаться рядом с соответствующими UI-компонентами.

Пример:

```text
widgets/hero/
└── ui/
    ├── Hero.tsx
    └── Hero.module.scss
```

Глобальные стили и общие design tokens допускается размещать в:

```text
app/styles/
shared/config/
```

Распределение определяется назначением:

- компонентные стили — рядом с компонентом;
- глобальный reset и подключение глобальных CSS — уровень приложения;
- переиспользуемые design tokens — общая инфраструктура стилизации.

Не рекомендуется создавать отдельную глобальную директорию со стилями всех компонентов приложения.

### D-26. Где хранить Layout, Header и Footer?

Рекомендуемое распределение:

```text
app/layouts/
widgets/site-header/
widgets/site-footer/
```

`Layout` определяет общую структуру приложения или его части.

`Header` и `Footer` могут быть самостоятельными композиционными widgets.

Если layout уникален для одной страницы, его допустимо разместить внутри page slice.

Универсальный layout-примитив без привязки к приложению может находиться в `shared/ui`.

### D-27. Как работать с Astro, где `src/pages` уже используется маршрутизатором?

Для Astro допускается следующая организация:

```text
src/
├── pages/     # Astro route entrypoints
├── views/     # Логические FSD pages
├── widgets/
├── features/
├── entities/
├── shared/
└── app/
```

`views` — физическое имя для логического FSD-слоя `pages`, а не дополнительный архитектурный слой.

Файлы в `src/pages` выступают точками входа маршрутов.

В небольших проектах можно не создавать `views` и размещать композицию непосредственно в Astro route-файлах.

Важно зафиксировать один вариант в рамках проекта.

Технические особенности Astro — server rendering, islands, client directives — должны учитываться без нарушения функциональных границ.

### D-28. Где хранить картинки, иконки и другой контент?

Расположение определяется областью использования.

Примеры:

```text
shared/assets/logo.svg
widgets/hero/assets/hero-background.webp
pages/about/assets/team-photo.webp
```

Если изображение относится только к одному модулю, его удобно хранить рядом с этим модулем.

Общие изображения, шрифты и иконки могут находиться в `shared/assets`.

Для файлов, которые должны быть доступны по неизменяемому публичному URL, используется предусмотренная фреймворком публичная директория, например `public/`.

Размещение публичных файлов не отменяет логическую принадлежность ресурса соответствующему модулю.

### D-29. Где хранить тесты?

Тесты рекомендуется располагать рядом с проверяемыми модулями.

Пример:

```text
entities/product/
└── model/
    ├── calculatePrice.ts
    └── calculatePrice.test.ts
```

Допускаются отдельные директории для интеграционных и end-to-end тестов.

Например:

```text
tests/
├── e2e/
└── integration/
```

Главное — сохранять понятную связь тестов с функциональностью и её ответственностью.

Для Domain предпочтительны независимые unit-тесты, для пользовательских сценариев — интеграционные или E2E-проверки в зависимости от риска.

## 8. Работа с архитектурными исключениями

### D-30. Можно ли нарушить правило ради практической необходимости?

Обязательные архитектурные правила должны соблюдаться по умолчанию.

Если решение требует исключения, необходимо определить:

- почему стандартный подход не подходит;
- какие зависимости появятся;
- какие альтернативы рассмотрены;
- как решение влияет на сопровождение;
- требуется ли ограничение или последующий пересмотр исключения.

Значимые исключения рекомендуется фиксировать в проектной архитектурной документации или ADR.

Не следует создавать исключение исключительно ради сокращения количества импортов или файлов.

### D-31. Нужно ли рефакторить старый код, который нарушает стандарт?

Необязательно сразу.

Для существующих проектов применяется постепенное внедрение архитектуры.

При работе с проблемным модулем рекомендуется:

1. Определить текущие обязанности.
2. Выявить нарушения зависимостей.
3. Оценить возможность безопасного разделения.
4. Внести улучшения в пределах задачи.
5. Зафиксировать оставшиеся нарушения, если их невозможно устранить сразу.

Не следует выполнять масштабную перестройку приложения исключительно ради соответствия новой структуре каталогов.

Подробнее: [Migration](migration.md.md).

## 9. Алгоритм принятия решения

Перед добавлением нового модуля разработчик должен ответить на несколько вопросов.

### Шаг 1. Какая ответственность у кода?

- Страница или экран → `pages`.
- Крупная самостоятельная UI-композиция → `widgets`.
- Пользовательская функциональность → `features`, если оправдано выделение.
- Бизнес-понятие → `entities`, если нужна самостоятельная модель.
- Универсальный технический код → `shared`.
- Глобальная конфигурация и инициализация → `app`.

### Шаг 2. Нужно ли выделять отдельный slice?

Проверить:

- существует ли самостоятельная ответственность;
- есть ли повторное использование;
- улучшится ли изоляция изменений;
- нужен ли независимый Public API;
- не создаёт ли выделение лишнюю связанность.

Если оснований недостаточно, оставить код внутри существующего slice.

### Шаг 3. Какие логические области есть внутри модуля?

Определить:

- UI;
- Domain;
- Application;
- Infrastructure.

Выделять только существующие обязанности.

### Шаг 4. Нужны ли отдельные файлы?

Разделять код, когда это улучшает:

- читаемость;
- независимость;
- тестируемость;
- сопровождение;
- контроль зависимостей.

Не создавать файлы только ради формального соответствия архитектурному шаблону.

### Шаг 5. Проверить зависимости

Убедиться:

- нет запрещённых межслойных импортов;
- нет нежелательных cross-imports;
- внешний код использует Public API;
- чистая бизнес-логика не зависит от UI и инфраструктуры;
- отсутствуют циклические зависимости.

## 10. Антипаттерны

### Глобальная техническая группировка

```text
components/
hooks/
stores/
services/
utils/
```

Если такая структура распределяет связанную функциональность по всему проекту, рекомендуется переход к функциональной декомпозиции.

### Избыточное выделение features

```text
features/open-dropdown/
features/close-dropdown/
features/toggle-checkbox/
```

Простое локальное UI-поведение не требует отдельной feature.

### Shared как склад бизнес-логики

```text
shared/lib/calculateOrderDiscount.ts
shared/lib/validatePromocode.ts
```

Доменные правила должны принадлежать функциональным или доменным модулям.

### Business logic внутри UI

```text
Component
├── fetch
├── DTO mapping
├── business validation
├── business calculations
└── rendering
```

Рекомендуется отделить чистые бизнес-правила и внешние интеграции.

### Избыточная Clean Architecture

```text
CreateButtonUseCase
ButtonRepository
ButtonRepositoryImpl
ButtonRepositoryFactory
```

Создание подобных абстракций без самостоятельных бизнес-сценариев обычно не оправдано.

### Преждевременная декомпозиция

Создание множества slices до появления соответствующих обязанностей затрудняет навигацию и увеличивает число публичных контрактов.

Предпочтительно начинать с локальной реализации и выделять модули при появлении обоснованных причин.

## 11. Контрольный список для Code Review

- [ ] Код расположен в модуле с понятной ответственностью.
- [ ] Выбран подходящий FSD-слой.
- [ ] Новый slice действительно необходим.
- [ ] Нет запрещённых импортов между slices и layers.
- [ ] Public API используется корректно.
- [ ] Бизнес-правила отделены от UI.
- [ ] Внешние интеграции не проникают в чистую логику.
- [ ] Application Use Cases и Ports созданы только при наличии необходимости.
- [ ] Общая функциональность размещена у корректного владельца.
- [ ] Не создано лишних абстракций и каталогов.
- [ ] Решение соответствует согласованной структуре проекта.
- [ ] Необходимые исключения обоснованы.
