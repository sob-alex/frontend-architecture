# Project Architecture Levels

## 1. Назначение

Документ описывает, как выбирать и развивать структуру frontend-проекта в зависимости от его сложности.

В компании используется **единый архитектурный подход**:

- Feature-Sliced Design — для организации функциональных модулей и зависимостей между ними.
- Clean Architecture Principles — для разделения ответственности и изоляции бизнес-логики.
- Progressive Architecture — для постепенного усложнения физической структуры по мере возникновения необходимости.

Простые и сложные проекты используют одинаковые фундаментальные правила, но могут существенно различаться количеством layers, slices, segments и архитектурных абстракций.

**Размер проекта определяет не набор обязательных архитектурных принципов, а необходимую степень декомпозиции.**

## 2. Общий подход

Архитектура должна соответствовать текущей сложности приложения и допускать его дальнейшее развитие.

Основные правила:

1. Начинать с минимально достаточного набора FSD-слоёв.
2. Группировать связанный код по функциональной ответственности.
3. Соблюдать направление зависимостей с начала разработки.
4. Разделять бизнес-логику, UI и инфраструктуру независимо от размера проекта.
5. Добавлять новые slices и segments при появлении самостоятельных обязанностей.
6. Применять Use Cases, Ports и Adapters там, где они решают конкретные задачи.
7. Не создавать каталоги и абстракции исключительно ради соответствия шаблону.

Для функциональности без самостоятельной бизнес-логики не требуется искусственно создавать Domain или Application.

При этом появляющиеся бизнес-правила должны быть независимы от UI и внешней инфраструктуры.

## 3. Что определяет сложность проекта

Количество страниц и компонентов не является достаточным критерием сложности.

На архитектурные решения влияют:

| Критерий | На что влияет |
|---|---|
| Количество функциональных областей | Потребность в отдельных slices |
| Количество страниц | Организация page slices и widgets |
| Переиспользование функциональности | Выделение features, entities и widgets |
| Сложность бизнес-правил | Разделение Domain и Application |
| Количество интеграций | Изоляция API и инфраструктуры |
| Сложность состояния | Организация model и presentation state |
| Командная разработка | Чёткость границ, Public API и правил импортов |
| Ожидаемое развитие | Необходимость устойчивых границ модулей |

Например, сайт из 30 статических страниц может быть архитектурно проще одностраничного конструктора интерфейсов со сложными правилами и состояниями.

**Сложность оценивается не только для проекта целиком, но и для отдельных функциональных модулей.**

## 4. Уровни организации

Выделяются три ориентировочных уровня.

Они помогают выбрать начальную структуру, но не являются жёсткой классификацией.

| | Простой | Средний | Сложный |
|---|---|---|---|
| Основной характер | Страницы и UI | Самостоятельные функции | Сложные сценарии и бизнес-правила |
| FSD | Минимальные слои | Нужные функциональные слои | Все необходимые слои |
| Widgets | По необходимости | Часто | Часто |
| Features | Редко | По необходимости | Часто |
| Entities | Редко | По необходимости | Часто |
| Чистая бизнес-логика | Обязательна, если есть | Обязательна, если есть | Обязательна, если есть |
| Use Cases | По необходимости | Для сложных сценариев | Для сложных сценариев |
| Ports / Adapters | По необходимости | При наличии значимых внешних зависимостей | Для изоляции зависимых от внешнего мира сценариев |

Наличие всех слоёв FSD не является признаком более качественной архитектуры.

### 4.1. Простой проект

Типичные примеры:

- лендинг;
- сайт-визитка;
- небольшой промосайт;
- статический корпоративный сайт;
- простая страница продукта.

Характеристики:

- преимущественно статический UI;
- небольшое количество интерактивности;
- минимум внешних интеграций;
- отсутствие сложной бизнес-логики;
- небольшое количество самостоятельных функциональных сценариев.

#### Рекомендуемая структура

Для проекта без ограничений файловой маршрутизации:

```text
src/
├── app/
├── pages/
└── shared/
```

При появлении крупных независимых композиционных блоков:

```text
src/
├── app/
├── pages/
├── widgets/
└── shared/
```

Слои `features` и `entities` не создаются заранее.

#### Пример: Astro Landing

У Astro директория `src/pages` отвечает за файловую маршрутизацию. Поэтому в многостраничном проекте допускается использование `views` как физического представления логического слоя FSD `pages`.

```text
src/
├── pages/
│   ├── index.astro
│   └── about.astro
│
├── app/
│   ├── layouts/
│   │   └── BaseLayout.astro
│   └── styles/
│       └── global.css
│
├── views/
│   ├── home/
│   │   ├── ui/
│   │   │   ├── HomePage.astro
│   │   │   ├── HeroSection.astro
│   │   │   └── ServicesSection.astro
│   │   └── index.ts
│   └── about/
│       ├── ui/
│       │   └── AboutPage.astro
│       └── index.ts
│
├── widgets/
│   ├── site-header/
│   ├── site-footer/
│   └── contact-section/
│
└── shared/
    ├── ui/
    │   ├── button/
    │   └── container/
    └── assets/
```

В данном примере:

- `src/pages` — технические entrypoints маршрутов;
- `views` — логические page slices;
- `widgets` — крупные самостоятельные блоки, используемые страницами;
- `shared` — универсальные UI-компоненты и технические модули;
- `app` — глобальная конфигурация, shell и layouts.

`HeroSection` остаётся внутри `views/home`, поскольку используется только на главной странице.

Если Hero становится переиспользуемым композиционным блоком нескольких страниц, его можно выделить в `widgets/hero`.

Для одностраничного небольшого сайта допустимо обойтись без `views`, размещая композицию непосредственно в `src/pages/index.astro`.

#### Clean Architecture

На простом проекте её принципы также действуют.

Если проект состоит исключительно из статической разметки, выделять доменные модули не требуется.

Если появляется расчёт цены:

```text
features/
└── price-calculator/
    ├── model.ts
    ├── ui/
    │   └── PriceCalculator.tsx
    └── index.ts
```

В `model.ts` располагается чистая логика расчёта, а в UI — отображение и обработка пользовательского ввода.

В этом случае выделение отдельной директории `domain/` или `application/` не требуется.

#### Чего следует избегать

Не рекомендуется создавать:

- пустые `features` и `entities`;
- Use Cases для обычных статических компонентов;
- Repository Interfaces при отсутствии соответствующих сценариев;
- отдельный slice для каждой секции или кнопки;
- глобальные stores без реальной потребности.

**Цель: минимальная структура с корректными границами ответственности.**

### 4.2. Средний проект

Типичные примеры:

- многостраничный корпоративный сайт с интерактивностью;
- каталог продуктов;
- личный кабинет с несколькими разделами;
- SPA с формами и внешними API;
- информационный портал с пользовательскими действиями.

Характеристики:

- несколько самостоятельных функциональных областей;
- повторно используемые компоненты и сценарии;
- интеграции с backend;
- локальное и глобальное состояние;
- доменные модели;
- умеренная бизнес-логика.

#### Рекомендуемая структура

```text
src/
├── app/
│   ├── providers/
│   ├── router/
│   └── styles/
│
├── pages/
│   ├── catalog/
│   ├── product-details/
│   └── cart/
│
├── widgets/
│   ├── site-header/
│   └── product-catalog/
│
├── features/
│   ├── add-to-cart/
│   └── filter-products/
│
├── entities/
│   ├── product/
│   └── cart/
│
└── shared/
    ├── ui/
    ├── api/
    ├── lib/
    └── config/
```

Это пример возможного набора слоёв, а не обязательный шаблон для каждого среднего проекта.

Если у приложения нет самостоятельных entities, слой можно не создавать.

Если бизнес-действия используются исключительно внутри страницы и не требуют независимого сопровождения, их можно оставить в page slice.

#### Организация функциональности

Пример feature:

```text
features/
└── add-to-cart/
    ├── ui/
    │   └── AddToCartButton.tsx
    ├── model/
    │   └── useAddToCart.ts
    ├── api/
    │   └── addToCart.ts
    └── index.ts
```

Здесь:

- `ui` отвечает за пользовательское взаимодействие;
- `model` — за состояние и координацию;
- `api` — за взаимодействие с внешним сервисом.

Если сложных бизнес-правил нет, отдельный Use Case создавать необязательно.

Если появляется самостоятельный сценарий, его можно выделить в чистую функцию Application.

#### Clean Architecture

В среднем проекте рекомендуются:

- отделение доменных правил от UI;
- локализация внешних интеграций;
- изоляция DTO при необходимости;
- разделение presentation state и бизнес-правил;
- отдельные application-сценарии при наличии сложной координации операций.

Dependency Inversion применяется избирательно, когда независимость сценария от инфраструктуры имеет практическую ценность.

**Цель: выделение устойчивых функциональных границ без лишних уровней абстракции.**

### 4.3. Сложный проект

Типичные примеры:

- CRM;
- ERP;
- сложная административная панель;
- финансовый кабинет;
- графический редактор;
- конструктор интерфейсов;
- система с многошаговыми бизнес-процессами.

Характеристики:

- сложные доменные правила;
- взаимосвязанные функциональные сценарии;
- несколько внешних интеграций;
- значительное количество состояния;
- высокая цена ошибок;
- несколько команд или длительный жизненный цикл проекта.

#### Рекомендуемая структура

```text
src/
├── app/
│   ├── providers/
│   ├── router/
│   └── composition/
│
├── pages/
│   ├── orders/
│   ├── checkout/
│   └── account/
│
├── widgets/
│   ├── orders-table/
│   └── checkout-summary/
│
├── features/
│   ├── submit-order/
│   ├── apply-promocode/
│   └── cancel-order/
│
├── entities/
│   ├── order/
│   ├── product/
│   └── promocode/
│
└── shared/
    ├── ui/
    ├── api/
    ├── lib/
    └── config/
```

Даже здесь не обязательно использовать все возможные segments внутри каждого slice.

#### Сложный slice

```text
features/
└── submit-order/
    ├── ui/
    │   ├── SubmitOrderButton.tsx
    │   └── useSubmitOrder.ts
    │
    ├── model/
    │   ├── submitOrder.ts
    │   └── ports.ts
    │
    ├── api/
    │   ├── httpOrderGateway.ts
    │   ├── dto.ts
    │   └── mapper.ts
    │
    └── index.ts
```

Ответственность:

- `ui` — Presentation;
- `model/submitOrder.ts` — Application;
- `model/ports.ts` — контракты;
- `api` — Infrastructure;
- `entities/order/model` — Domain.

Domain и Application не должны зависеть от конкретных внешних адаптеров.

#### Когда требуется дополнительное разделение

При росте логики можно выделить:

```text
model/
├── domain/
│   ├── rules.ts
│   └── types.ts
│
├── application/
│   ├── useCases.ts
│   └── ports.ts
│
└── presentation/
    └── useFeature.ts
```

Однако такие каталоги не создаются по умолчанию.

Кроме того, если доменная модель относится к самостоятельной FSD entity, предпочтительно хранить её в соответствующем `entities/*/model`, а не дублировать в feature.

**Цель: обеспечить управляемость сложной бизнес-логики и независимость сценариев от технических деталей.**

## 5. Архитектура развивается на уровне модулей

Не все части проекта должны иметь одинаковую внутреннюю сложность.

Например, в большом приложении могут одновременно существовать:

```text
widgets/
└── site-header/
    ├── ui/
    │   └── SiteHeader.tsx
    └── index.ts

features/
└── toggle-theme/
    ├── model.ts
    ├── ui/
    │   └── ThemeSwitcher.tsx
    └── index.ts

features/
└── submit-order/
    ├── ui/
    ├── model/
    │   ├── submitOrder.ts
    │   └── ports.ts
    ├── api/
    │   └── httpOrderGateway.ts
    └── index.ts
```

Все три модуля могут соответствовать архитектурному стандарту.

Не требуется приводить структуру простого компонента к структуре наиболее сложной feature.

**Сложность внутренней организации определяется ответственностью конкретного модуля, а не размером всего приложения.**

## 6. Когда усложнять структуру

Расширение архитектуры должно быть связано с конкретными изменениями требований.

| Ситуация | Возможное действие |
|---|---|
| UI-блок используется на нескольких страницах | Рассмотреть выделение widget |
| Функциональность стала самостоятельной | Рассмотреть выделение feature |
| Бизнес-модель используется в разных сценариях | Рассмотреть выделение entity |
| Файл содержит несколько независимых обязанностей | Разделить по ответственности |
| Появились сложные бизнес-правила | Выделить чистый Domain |
| Появился многошаговый сценарий | Выделить Application / Use Case |
| Сценарий зависит от внешних сервисов | Рассмотреть Ports / Adapters |
| Возникли циклические зависимости | Пересмотреть границы модулей |
| Несколько slices одного слоя зависят друг от друга | Рассмотреть объединение или композицию сверху |

### Важно

Количество строк, файлов и компонентов может служить сигналом для анализа, но само по себе не является основанием для изменения архитектуры.

Например, компонент на 300 строк не обязательно нужно превращать в widget.

И наоборот, небольшую функцию с критическим бизнес-правилом может быть полезно изолировать сразу.

## 7. Когда не нужно усложнять структуру

Не рекомендуется вводить новые архитектурные элементы исключительно потому, что:

- проект потенциально может стать большим;
- в другом проекте уже используется аналогичный слой;
- определённый паттерн считается хорошей практикой;
- можно создать дополнительный интерфейс;
- появилась одна небольшая функция;
- компонент используется дважды внутри одного slice;
- файл достиг условного количества строк.

Перед добавлением абстракции необходимо понять, какую ответственность она изолирует и какие зависимости помогает контролировать.

При отсутствии убедительных причин предпочтительно оставить более простую реализацию.

## 8. Процедура выбора архитектуры нового проекта

Перед началом разработки необходимо определить:

### Шаг 1. Характер проекта

Оценить:

- количество страниц и функциональных областей;
- наличие бизнес-логики;
- количество интеграций;
- предполагаемые источники данных;
- требования к состоянию;
- ожидаемую командную разработку.

### Шаг 2. Выбрать базовые слои FSD

Начать с минимального набора:

```text
app/
pages/
shared/
```

С учётом особенностей фреймворка допускается адаптация физических директорий.

Добавить `widgets`, `features` и `entities`, если их ответственность уже очевидна.

### Шаг 3. Определить функциональные границы

Разместить уникальную функциональность внутри соответствующих page slices.

Заранее известные переиспользуемые или самостоятельные модули допускается выделять сразу.

### Шаг 4. Определить границы бизнес-логики

Если бизнес-логика существует, определить:

- доменные правила;
- application-сценарии;
- внешние зависимости;
- презентационную логику.

Логические области не обязательно должны соответствовать отдельным директориям.

### Шаг 5. Зафиксировать решения

В проектной архитектурной документации указать:

- используемые FSD-слои;
- адаптации под фреймворк;
- основные функциональные slices;
- особенности внутренних зависимостей;
- существенные отклонения от корпоративного стандарта.

## 9. Развитие существующих проектов

Для существующего проекта не требуется немедленный переход к максимально полной структуре FSD.

Рекомендуется:

1. Определить текущие функциональные границы.
2. Найти циклические и нежелательные зависимости.
3. Выбрать участок, который нуждается в рефакторинге.
4. Локализовать связанную функциональность.
5. Выделить чистую бизнес-логику.
6. Сформировать Public API и проверить зависимости.
7. Повторить процесс для следующих участков.

Рефакторинг должен быть инкрементальным и контролируемым.

Отдельные старые и новые модули могут временно иметь разную физическую структуру.

Это допустимо, если переход к целевой архитектуре управляем и не увеличивает связанность приложения.

Подробнее: [Migration](migration.md.md).

## 10. Контрольный список

Перед утверждением структуры проекта:

- [ ] Используется минимально необходимое количество FSD-слоёв.
- [ ] Функциональность сгруппирована по ответственности.
- [ ] У страниц есть понятные границы.
- [ ] Widgets, features и entities выделены обоснованно.
- [ ] Соблюдаются правила импортов FSD.
- [ ] Чистая бизнес-логика не зависит от UI и инфраструктуры.
- [ ] Количество файлов и каталогов соответствует сложности модулей.
- [ ] Не создаются пустые слои и segments.
- [ ] Учтены особенности используемого фреймворка.
- [ ] Архитектура допускает дальнейшее развитие без полной реорганизации проекта.
